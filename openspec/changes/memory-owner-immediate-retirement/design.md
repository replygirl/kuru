# Design

## Context

The per-project memory owner (`kuru memory-service` process; it runs Dolt through the owned supervisor) serves attachments from a `JoinSet` in `serve_until_idle_with` (`packages/kuru-memory/src/service.rs`). When the set is empty it waits `SERVICE_IDLE_TIMEOUT` (30 s) for a new accept and then closes: store close (write drain, pools, supervisor and Dolt reap), then endpoint retirement, then the Owner lock drop. The maintainer decided there is no idle window. Removing it exposes behaviour the grace was hiding:

- **Starter race.** The starter's post-spawn loop polls `try_attach` every 100 ms and fails with "memory service exited before readiness" on any child exit. `attach_existing` (read-only commands) and writable clients waiting for Start also poll `try_attach`. If any attachment made a fresh owner retire on detach, a `kuru memory status` could retire a fresh owner inside one of the starter's poll gaps.
- **Cancelled calls.** `ServiceAttachment::call_with_id` takes the stream out and restores it only after a complete reply. A cancelled or failed exchange drops the connection; the next call reconnects lazily through `AttachmentFactory::connect` to the same generation. With no grace, an Esc on a client's only connection retires the owner under a running TUI and the next call fails.
- **Checked recovery.** Recovery reaches the successor through `attach_or_start`, then drops (or consumes into a candidate view) its attachment before `reopen_after_checked_recovery`; the reached successor would retire and the reopen would elect another owner.
- **Racing clients.** A client that meets a retiring owner can see an unmapped Windows `ERROR_PIPE_NOT_CONNECTED` (233) or a fatal "private pipe connect timed out" after a busy pipe; `request_idle_retirement` treats a peer-closed handshake as an error.
- **Order.** Today Dolt is reaped before the endpoint is retired, so a client can read an endpoint whose owner is no longer accepting.

All dream execution is client-side (`packages/kuru-runtime/src/dream.rs`); the owner's only dream state is the per-connection dream lease. The only owner task that outlives its handler is the detached candidate writer in `store.rs`, which takes `shared.write` inside its task; `MemoryStore::close` takes `shared.write` first, so such a writer finishes before the reap or never starts.

## Goals / Non-Goals

**Goals:**
- The owner retires as soon as no attachment remains and no accepted work is pending, once its starter has attached.
- A fresh owner cannot be retired by a client other than its starter before the starter attaches.
- A running writable client keeps the owner across a cancelled or failed call, with no request resent.
- Checked recovery ends on the verified successor.
- A client racing a retiring owner elects a successor within its unchanged startup budget; no error from the race alone.
- Shutdown order: stop accepting, retire endpoint, close store and reap Dolt, release the Owner lock.

**Non-Goals:**
- No raised deadline, no retry added to hide a fault, no change to the meaning or range of `memory.startup_timeout_secs`.
- No weakening of isolation, ownership, recovery or the uncertain-write fence.
- No sleeps in tests; waits are event hooks bounded by existing fixture backstops.
- A dream that outlives its client (a new feature).
- A `PROTOCOL_MINOR` bump or a session-anchor protocol call.
- Owner-side distinction between read-only and writable attachments.

## Decisions

**D1. Pending work is the attachment set plus the close drain.** The serve loop's `attachments` `JoinSet` is non-empty while any handler runs; `serve_attached` handles one request at a time, so an accepted request whose client vanished holds the owner until its handler returns. A dreaming client is an attached client. `shared.uncertain` and `ReceiptProgress` are not pending work: a successor answers from durable receipts. Rejected: an owner-side work counter or lease, which duplicates what the attachment set already proves.

**D2. Two empty states.** `Retirement` gains `reached: AtomicBool`. Not reached and empty: the loop `select!`s on accept (bounded by `OWNER_LOCK_RECHECK_INTERVAL`), an absolute deadline `published + startup_timeout_secs` (the instant after `record.publish`), and the retirement notify; an accept timeout is `continue`; deadline expiry is a clean exit with a warn-level log. Reached and empty: `break` at once. Non-empty: unchanged. `SERVICE_IDLE_TIMEOUT` is deleted; the busy accept bound is renamed `OWNER_LOCK_RECHECK_INTERVAL` (35 s). The starter's own deadline begins before the owner's, so a live starter attaches before the owner gives up on it. Rejected: an extra accept poll before breaking; Tokio caches accept readiness and neither OS offers atomic check-and-close, so correctness rests on the client re-entering election when its connection loses the race.

**D2a. Starter token.** Crate-private `OpenOptions::starter_token: Option<Uuid>`. `attach_or_start` uses the supplied token or creates a UUID v4 immediately before `spawn_service`; `service_arguments` appends it as an optional tenth argument; `parse_service_arguments` accepts nine or ten, requires a valid UUID in the tenth, rejects anything after. `ClientHello` gains `starter_token: Option<String>` with `serde(default, skip_serializing_if = "Option::is_none")` (the hello is `deny_unknown_fields`, so a hello without a token serializes as today); only the starter's post-spawn attach fills it; `Debug` leaves it out. `serve_attached` sets `reached` after `accept_handshake` succeeds and the presented token equals the owner's; an owner started without a token sets `reached` on any authenticated handshake (mixed-version fallback). The token is not a secret. The same token tags unit 2's activity record, which the owner then writes on every start (decided).

**D3. Cancelled calls: Option B, eager.** `ServiceAttachment` gains `held: Option<LocalStream>` and `retain_after_abandon: bool`. `new_view` sets the flag on a writable main-view primary (successor branches that turn a recovery attachment into a candidate view use a separate constructor that does not); a replacement inherits the flag from the attachment it replaces (the lazy path in `checked_call_locked` copies it, since that function cannot tell the primary from an extra connection). A drop guard in `call_raw`'s primary branch, created unarmed, armed by `checked_call` for a retaining attachment once the stream the call will use is live (including one its lazy connect has just opened; a lazy connect that fails or is cancelled leaves it unarmed, since that connect was itself the replacement attempt and nothing retries it) and disarmed after a complete exchange, spawns a replacement task when `Handle::try_current()` succeeds. Under the primary's mutex the task: upgrades `Weak`s to the primary and session (stops if gone); stops if the session is closed or the attachment has a live stream or no held stream; `factory.connect()`; re-checks `closed` under the same lock; installs the new attachment, which drops the old one and its held stream afterwards. `RemoteSession::close` locks the same mutex, so close and replacement are totally ordered. `ServiceAttachment::close()` clears both `stream` and `held`, in `service.rs`, because retained `Arc` clones would otherwise keep a held stream alive past `MemoryStore::close`. Forks (dream lease, candidate, export) keep today's drop-at-cancel. No request is resent; the caller gets the original error; `PendingMutation::drop` still sets the fence. Sole-attachment checks (`active == 1`) are unchanged: during the overlap a client counts twice, and an abandon issued in the tail is refused `Active`, truthfully; a retry succeeds.

- **Safety margin, asserted.** Replacement time is bounded by connect (`HANDSHAKE_TIMEOUT`, 5 s) plus the hello write and reply read (each `HANDSHAKE_TIMEOUT`) = 15 s, which must stay shorter than the owner's shortest end of an abandoned connection, `OPERATION_TIMEOUT` (35 s, a partial frame or an oversized reply write). A compile-time `const` assertion over the existing constants (`3 * HANDSHAKE_TIMEOUT < OPERATION_TIMEOUT`, placed in `rpc.rs` beside `Retirement`, where the private `OPERATION_TIMEOUT` is in scope and the already public `super::HANDSHAKE_TIMEOUT` is reachable, so no visibility or value changes) carries a comment saying why; it fails the build if either constant moves across the margin.
- **Refused replacements.** The owner drops a new connection without a reply at `MAX_ATTACHMENTS` and during a candidate-resolution reservation. Policy: keep the held stream, add no retry loop; the next call's existing lazy connect is the second attempt, and it builds the new attachment before dropping the old one, so the overlap is kept there too.
- **Not covered, stated plainly.** (1) The owner closing a live client's only connection on its own (a request-frame decode error, which is a bug; or a 35 s mid-write stall, which needs the frame budget exhausted by other connections, so the owner is not at zero). (2) A refused replacement followed by the owner's 35 s timeout on the abandoned connection before the next call. (3) A future dropped outside a runtime spawns no task; the lazy connect and the two 35 s owner-side ends apply. In each case the owner may retire and the client's next call fails with a truthful connect error; nothing is retried to hide it. The same text goes into `docs/memory.md`.
- Rejected: **Option A** (session anchor call). It needs `PROTOCOL_MINOR` 7 to 8 (updated commands hard-fail against a still-running old owner), UUID-matched sole-attachment rules, an async `new_view` and a new owner-side state machine, for about three times B's surface. Rejected: **lazy-only B**, which cannot hold the owner across the minutes between a cancel and the next call.

**D4. Plain transport loss never reconnects through `attach_or_start`.** A replacement only goes to the same generation through the session's `AttachmentFactory`.

**D5. Shutdown order.** Loop breaks (Owner lock held) → `drop(listener)` → `record.retire` (removes `endpoint.json` only if generation and secret match) → `store.close()` (write drain, pools, supervisor and Dolt reap; lifecycle lease released at the reap) → `lock.verify()`, explicit unlock, drop → exit. A failure retiring the record does not skip the store close; the first error is returned; the Owner lock is released only after the store close has returned. The `ServiceOwner` comment becomes "normal shutdown retires discovery, then reaps Dolt before releasing owner authority".

**D6. Racing clients.** Accepted before the break: attaches to the live owner. Connected but not accepted: peer-closed, mapped to `None` (Windows raw OS error 233 added to `is_peer_closed`). Record read but not connected: `NotFound` or refused → `None`; on Windows a busy pipe through the connect deadline → `None` via D11. No record: `None`. After `None` the client takes Start, loops on the Owner probe while busy and spawns only once the Owner lock is free (after step 5 of D5), so two owners cannot overlap. `request_idle_retirement` maps a peer-closed handshake to `None`. The "did not publish a valid endpoint" error becomes "the previous memory service was still shutting down or did not publish a valid endpoint within memory.startup_timeout_secs".

**D7. Explicit unlock.** `ServiceLock::release(self)`: `verify`, `File::unlock`, drop. Used for the Owner lock at shutdown, both Owner probes, and Start on every return from `attach_or_start`. On Unix a child between fork and exec can hold a duplicate lock description; an explicit unlock releases it for every duplicate. `ServiceOwner::open` stays single-attempt.

**D8. Read-only sessions.** A read-only primary has `retain_after_abandon = false`: no hold, no replacement, no successor rebind. A cancelled read drops its connection as today; a later lazy connect either reaches the same generation or fails with "the memory service ended while this read-only command was disconnected; run the command again". Decided reading: the owner cannot tell read-only from writable attachments, so an open read-only connection counts as an attachment while it exists and an in-flight read is pending work, as today.

**D9. `attach_existing` probes the Owner lock only after a non-blocking Start acquire succeeds**, then releases both. If Start is busy it skips the probe and keeps polling `try_attach` until its deadline. While `attach_existing` holds Start no owner can be in its single-attempt Owner acquire.

**D10. Checked recovery ends on the verified successor.** `RemoteSession.successor: Mutex<Option<ServiceAttachment>>`. Each successor branch stores a clean main-view attachment there before returning (the recovery attachment itself where it would be dropped, or `attachment.fork()` before it is consumed into a candidate view). `RemoteSession::close` is split into a drain (mark closed, close every registered attachment) and the explicit close (drain, then drop the slot). `reopen_after_checked_recovery` drains, then takes the slot and uses it in place of `attach_or_start` after the same `store_instance` check; without one it uses `attach_or_start`. A reopen cancelled during its drain therefore keeps the slot for the next reopen; one cancelled after taking it drops it, and a later reopen uses the existing election path. The slot is stored under its lock only while the session is not closed (it is filled before `retire_after_checked_recovery` marks the session closed), so it cannot outlive a racing explicit close. A fork taken for a consumed branch that fails leaves the slot empty with a warning; the returned candidate view still holds the successor, and the reopen elects as before. **Effect on sole-attachment checks, tested:** after recovery the session is closed and can issue nothing, so the slot is the session's only attachment on the successor. Another client's candidate abandon in that window sees `active == 2` and is refused `Active`, truthfully; the reopen adopts the slot as its primary instead of opening another connection, so after the reopen the session again counts once and its own abandon passes. The slot adds at most one attachment per session and is released by close, so `MAX_ATTACHMENTS` (32) against `MAX_PARALLEL_CLIENT_CONNECTIONS` (16) keeps its headroom. Tests T11 and T11a cover both effects.

**D11. Windows pipe marker.** In `kuru-platform/src/windows/pipe.rs`, when the connect deadline expires and the last retry error was `ERROR_PIPE_BUSY`, return `io::Error::new(io::ErrorKind::TimedOut, NoFreeInstance)` whose `Display` is exactly "private pipe connect timed out", plus `pub fn is_no_free_instance(&io::Error) -> bool`. Kind and message are byte-identical to today. Only `try_attach_observed` and `request_idle_retirement` check it; `AttachmentFactory::connect`, the supervisor rendezvous, the updater and the platform tests are unchanged. A genuinely saturated live owner keeps the Owner lock busy, so the caller still fails at its unchanged deadline.

**D12. No `PROTOCOL_MINOR` bump.** The token rides in the handshake hello, which is not part of the pinned protocol surface.

**D13. Spec deltas.** Four MODIFIED requirements: `project-memory-owner` "Attachment-bound idle cleanup", `project-memory-service` "Idle shutdown and safe recovery" and "Reachable exact-ref candidate resolution", `memory-store-lifecycle` "Explicit shared-store shutdown". The four misplaced shutdown scenarios are reworded in place under their existing names; moving them under the shutdown requirement was accepted by the maintainer but is refused by cospec 0.8.2 (`archive/scenario-preservation` rejects a MODIFIED requirement that drops a scenario name, with no override). The "Reconnect races idle shutdown" THEN clause is qualified "within its startup budget", as the requirement text is. The `## Purpose` line of `project-memory-service` ("retains idle service authority safely") is outside every requirement; it is a separate task, and whether archive can rewrite it is unverified.

**Test-support decisions.**
- In-process `ServedOwner::serve` defaults to admission "never reached" with no first-attachment deadline, so fixtures end by maintenance retirement, `restart` or lock loss as today. `ServedOwner::serve_with(ServeKnobs { admission: Starter(token) | AnyAttachment | Never, first_attachment, recheck, observer, close_pause })` drives the new tests. Condition (decided): retire-on-last-detach is also covered by really spawned owners (the rewritten `independent_clients_elect_one_real_process_...`, `separate_cold_starters_...`) and by the CLI end-to-end test T16, not only by in-process tests.
- Serve-loop observer (`AttachmentAccepted { active }`, `AttachmentJoined { remaining }`, `EnteredEmpty { reached }`, `LockRechecked`), `ClosePause` at four points, a replacement hook on `RemoteSession`, and a `cfg(test)` `DispatchPause` for reads.
- `test_support::await_owner_release(options)`: a blocking `File::lock` on the Owner lock file in `spawn_blocking`, then explicit unlock, bounded by the fixture backstop. It replaces every wait that read endpoint absence as "reaped"; every such test is audited by content, including what follows the polling in the Windows starter-Job test.
- **Logged-owner CLI test (decided, superseding the revised design's reordering).** Coverage of the CLI-to-logged-owner path is kept: the owner's diagnostic stderr is routed, through a test-support environment hook forwarded like `lifecycle_trace::forwarded()`, to whichever owner the CLI child elects, and the test asserts the `candidate_owner stage=ref_inspection ... fault=ref_rejected` line from that owner. `retire_idle_service` in that test is removed.

## Risks / Trade-offs

- [Every command now opens a fresh owner: about 0.6 s to open an existing project instead of about 0.014 s to attach (maintainer figures)] → Accepted by the maintainer decision. Measured early on macOS and Ubuntu (tasks 1.x); if a reopen right after a close typically waits more than about one second in total, implementation stops before merge and reports.
- [A reopen landing during a close waits for it inside the same `startup_timeout_secs`; worst-case close is about 29 s on Unix and 32 s on Windows plus a write drain, at or above the 30 s default] → Not raised or split. A close near its bound is a fault worth reporting; the reworded error names it. Close duration and reopen time are recorded per native platform (V1, V2).
- [Option B's uncovered fault cases (D3)] → The next call fails with a truthful error; documented.
- [Mixed versions: an old running client served by a new owner has no Option B; a cancel on its only connection retires the owner and its next call fails. A new starter with an old binary at `current_exe()` fails "exited before readiness". An old starter with a new owner falls back to "any attachment reaches", so the starter race exists only there] → Stated in the upgrade notes; ends when the session restarts. No new "protocol is incompatible" error.
- [Abandon refused `Active` in the overlap tail after a cancel] → Truthful refusal naming a real attachment; retry succeeds. Already happens today while a cancelled request runs.
- [Windows code (D6 code 233, D11 marker, Windows fixtures) is compiled on macOS only through the Windows-target lint] → Behaviour unverified until native Windows CI; V3 records the code a client actually sees.
- [A test's `await_owner_release` thread cannot be cancelled if the backstop fires] → The test has already failed; the thread ends with the process.

## Operational surface

- **Process topology.** Unchanged binaries and arches; the owner is still `current_exe()` spawned by the starter, on every supported platform. Its lifetime changes: it exits when the last attachment releases after its starter attached, or at `startup_timeout_secs` from publication if the starter never attached (warn-level log).
- **Arguments.** `kuru memory-service` accepts an optional tenth argument (a UUID starter token). Old owners reject it (loud, rare downgrade case).
- **Bind address and IPC.** Unchanged: Unix private socket and Windows private named pipe, owner-private endpoint record. The endpoint record is now retired before Dolt is reaped. No ports, no network exposure.
- **Connection limits.** `MAX_ATTACHMENTS` (32) and `MAX_PARALLEL_CLIENT_CONNECTIONS` (16) unchanged; Option B adds at most one held connection per writable session, and the successor slot at most one per recovering session.
- **Secrets.** None added. The starter token is not a secret and grants nothing beyond "this is my starter"; `Debug` omits it. The runtime connection secret is unchanged.
- **Timeouts.** `startup_timeout_secs` meaning and range (1-300 s) unchanged; `HANDSHAKE_TIMEOUT` 5 s and `OPERATION_TIMEOUT` 35 s unchanged; `SERVICE_IDLE_TIMEOUT` removed.
- **CI.** No workflow change. Native legs already run the memory, CLI and installation suites; Windows-only paths (D6, D11, the starter-Job tests) are proven there.
