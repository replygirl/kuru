## Context

`MemoryStore::open` currently acquires a project startup lock, starts a lifetime-pipe supervisor and returns branch-pinned SQL pools. A `Shared.write` mutex serializes only clones in one process. The CLI separately holds a project writer lease for the conversation, and `MemoryStore::close` stops its owned supervisor. The supervisor has strong identity, endpoint and reap guarantees that the service must retain. Existing message rows use a global auto-increment sequence; candidates reject a moved live base; operation and usage receipts reconcile uncertain writes.

## Goals / Non-Goals

**Goals:** Establish one on-demand owner process with attachable storage clients; preserve native ownership/recovery semantics; make the protocol suitable for P28's serialized mutations and P29's scoped history without committing those semantics prematurely.

**Non-Goals:** A remote listener, provider execution, session driving, approvals or cancellation of another runtime. This change does not allow concurrent conversation drivers or alter message/summary schemas.

## Decisions

### 1. A separate service process owns the existing `MemoryStore` and supervisor

Launch the ordinary executable in an internal service mode; it is already the verified carrier of the bundled Dolt engine. The service opens the store, owns all branch pools and retains the supervisor handle. `kuru-memory` keeps the same internal entry for native fixtures. Clients have only scoped attachment handles and cannot run supervisor teardown. The service process is independent of its starter's lifetime; no detached Dolt without an owning supervisor is allowed. Reject the alternative of prolonging a conversation process or making the current supervisor itself an application RPC server: both mix client and storage lifetimes, and the supervisor's lifetime-pipe/reap contract has a narrower purpose.

The first implementation may keep the existing SQL-backed `MemoryStore` method bodies behind a service client transport; the service is the only authority that creates them. The public store facade keeps its method names for runtime callers but its close drops the caller's attachment, not the shared owner. A small, typed operation protocol covers the used methods with bounded frames; raw SQL passwords, paths and arbitrary SQL are not client operations. Candidate handles are service-issued IDs bound to service generation and project. P28 then puts every mutating operation through the owner's advisory serialization without another application API migration.

Keep the current SQL store in the crate-private `store` module and publish a concrete `MemoryStore` facade at the crate root with local and attached backends. This preserves runtime method names and real-Dolt fixture access without a runtime trait migration or dummy SQL fields. The facade's shared closed state invalidates every clone of that client handle on explicit close; attached close releases only that attachment and never shuts down another client's owner. Candidate, usage-ledger and export handles carry the backend and service generation, and every operation returns a typed error if its generation is retired. An explicit managed open is used by the ordinary CLI under the existing conversation lease. Direct local writable opens for legacy fixtures must retain their own checked owner authority through Dolt cleanup and reject a live service owner, so test/compatibility paths cannot bypass service writer authority; read-only inspection attaches without taking owner lifetime authority.

An incomplete mutating exchange fences all clones and child handles of that logical client until the durable-service-operation-receipts prerequisite resolves its original logical ID. A generic storage-failure response also leaves the client fenced because it can conceal an accepted Dolt operation whose local reconciliation timed out; a complete wire frame alone is not definitive mutation evidence. Explicit typed pre-effect rejection and candidate conflict may leave the client usable. Reconnect never erases an unknown result or silently replays it.

### 2. Stable service election is separate from Dolt lifecycle locking

Use two retained, owner-private per-project locks under the existing external `memory/locks` hierarchy. A contender first tries the published private local endpoint and authenticated handshake. If unavailable, it acquires the short service-start lock, checks the endpoint again, and spawns the service. The child service acquires a distinct service-owner lock before opening the store and publishing its checked endpoint; the starter treats the authenticated handshake as readiness and releases its start lock only after that readiness or a definite child failure. If the starter crashes, another starter can acquire its lock but must wait for or reject a still-held owner lock, never launch a second engine. The service holds owner authority for its entire lifetime. The current store startup and stable lifecycle locks remain responsible for provisioning, migration, directory moves and Dolt reap; no file is unlinked merely because its recorded PID or port is stale. After a service crash, a successor must wait for the old supervisor's lifecycle lease/reap and run existing store reconciliation before admitting mutations. A held owner lock with an unresponsive endpoint is a bounded error, never takeover permission.

Reject using the existing project conversation lease for service election: it would prevent later concurrent sessions and does not distinguish storage ownership from session driving. The current CLI lease remains a temporary admission guard until P29/P30.

### 3. Private, versioned local IPC with generation-bound attachments

Use a Unix domain socket on Unix and a DACL-restricted named pipe through `kuru-platform` on Windows, in a checked owner-private directory outside the tool root. Connection bootstrap uses a fresh service generation and secret valid only for that running generation, published in a private checked endpoint record and retired on shutdown; never use persistent Dolt credentials as the client secret. Handshake checks protocol major/minor, canonical project scope/path, store instance, generation and compatible schema, with fixed frame-size and request deadlines. Unknown major versions, incompatible required features, wrong project, wrong instance and wrong generation fail explicitly. An old active service remains untouched; an update cannot replace it beneath clients. The privacy boundary is other OS users and unauthenticated callers; another process running as the same user and able to read the private endpoint record can attach, so this is not same-user process isolation.

Endpoint records are hints: a client must complete the authenticated handshake and the service must verify its own retained directory/lock identity before granting access. The service rechecks authorization on every request or attaches an unforgeable generation-bound capability to a live connection; dropped connections invalidate that capability. This avoids trusting a cached client handle after purge or restart. Reject loopback TCP as the public service endpoint: an occupied port is weak discovery authority and makes privacy and ownership harder across the three native platforms.

### 4. Idle lifetime follows live attachments and in-flight operations

Keep an explicit attachment count and operation permits. Disconnect/EOF releases a client's attachment after its accepted operations settle or reconcile. At zero attachments and zero in-flight operations, start a documented 30-second idle timer; a successful reconnect cancels it atomically. Idle shutdown closes store pools, awaits supervisor/Dolt reap and only then releases election/lifecycle authority and retires the endpoint. An explicitly requested purge holds the start-election gate and asks the authenticated owner to retire early only when its maintenance connection is the sole attachment. The owner then drains that connection, reaps Dolt and retires the generation before purge acquires the owner gate and moves storage. A live client causes a bounded refusal without changing its owner. Unexpected termination leaves the supervisor to reap Dolt by its existing lifetime-pipe contract. No stale PID probe initiates a kill.

Reject per-client reference files: they can outlive crashes and would need PID-based cleanup. Live IPC connections give native EOF and support a bounded heartbeat only if needed by a platform; tests must prove attachment cleanup on Windows and Unix. Dropping an attachment releases connection-owned candidate handles but never abandons a durable candidate; only an explicit checked promotion or abandonment may resolve that branch.

### 5. P28 mutation and maintenance contract is predeclared, not enabled here

P28 will make the service the sole writer. Its lock order is: service admission gate (shared for ordinary operations, exclusive for maintenance) → store advisory mutation lock → short SQL transaction/commit → receipt reconciliation before releasing mutation authority. No provider call or whole conversation holds the mutation lock. Directory-changing maintenance first excludes new clients and drains in-flight operations, then obtains the existing stable lifecycle lease before moving anything. Purge advances a service generation/tombstone so old clients cannot recreate the store; import and restore re-admit only after validation. The service-owned `Shared.write` mutex is a process implementation detail, not the cross-process contract; all writers must enter through the service.

Append allocation stays in Dolt through the existing `messages.sequence BIGINT AUTO_INCREMENT` column. P28 must prove with barrier-synchronized multi-process tests that serialized service appends retain every row with a unique, ordered sequence; it must not introduce a second allocator without evidence that the existing one fails the contract. Retried or uncertain appends use a stable invocation ID and durable receipt to return the original result, not add a new row. Sequence gaps are permitted, but duplicates and missing committed rows are not. The service serializes topology/state changes, dream promotion, forget and ledger operations; candidate promotion compares the live base under the mutation lock. An unrelated live append moving the base is an explicit promotion conflict.

The runtime retains the exact dream candidate and staged report across a lost candidate write or promotion reply. It uses the prerequisite's typed candidate-unit outcome to obtain a fresh checked handle before continuing, then the typed transition outcome to distinguish promotion, abandonment and still-open conflict. Staged topology publishes only from an exact promoted revision matching the captured candidate target; comparing live state values cannot prove that transition because a sibling may write them later. A still-open or conflicted ref remains available for explicit resolution and is never automatically abandoned because a promotion reply was lost. A cancelled pre-promotion dream waits for accepted unit writes to settle before a checked explicit abandonment.

An in-memory candidate handle alone is not a recovery surface after the conversation process exits. The owner therefore offers bounded, paged inspection of exact canonical Kuru candidate refs and their checked head/base/live relationship through the existing memory command boundary. It distinguishes an open unchanged ref, an open moved-base conflict, a transition whose result is still uncertain, and a resolved or missing ref; missing refs do not prove an earlier candidate write was absent. A selected explicit abandon carries the inspected exact ref and head, rechecks them under the owner's mutation authority, settles accepted writes and any pending transition by their typed proof, and refuses when those checks cannot establish a safe open ref. It uses the existing checked ref transition and no broad prefix deletion. The CLI exposes status and explicit abandon with a reviewed exact identity; the TUI uses its shared command registry for the same operations. This phase does not offer public manual promotion, three-way merge, historical lineage editing, automatic replay or automatic abandonment after an ambiguous promotion. The retained staged report remains private to the runtime/candidate view; status reports only bounded derived fields and marks unavailable evidence as unknown.

The owner excludes new attachments during selected abandonment with a temporary reservation on its existing admission counter. It admits the resolution only when the requesting attachment holds no candidate/export handles and no other attachment or accepted handler remains; inventory does not take this reservation. A selected abandonment has its own caller request UUID and exact branch/base/head identity. If its reply is lost, the client retains those fields and queries the existing typed candidate-transition outcome through a successor after verified old-owner/engine reap; it never invents the unavailable creation UUID or sends the abandonment again. An open, changed, or indeterminate result leaves the ref intact for another inspection, while only a proved Abandoned result reports success. Once an empty candidate's status ref is reclaimed, its target equals its base and absence cannot prove which request removed it; that result remains uncertain and fenced. Closing or reopening an inspection client does not settle the earlier request. The command reports an absent ref as absent with operation outcome unproved, not as a conflict or successful abandonment.

The exact-ref calls increment the minor service protocol: a newer client rejects an older active owner at handshake before it can send a selected mutation. A selected abandonment's in-flight key hashes its domain-separated exact branch/base/head tuple with its caller UUID; a different tuple or an invented same-generation UUID cannot borrow handler-settlement evidence. The typed outcome distinguishes an extant abandoned marker from a reclaimed ref. An extant exact abandoned marker proves the candidate's final state, not which request caused it. Reclaimed absence proves abandonment only after the registered handler completed or the old owner and engine were verified reaped; otherwise it remains uncertain.

### 6. P29 history integration is column-bound and mode-selected

P29 will add a durable nullable `session_id` on raw private part and relationship messages, with indexes supporting `(namespace, session_id, sequence)` suffix reads. New raw rows require a validated session ID; context queries select exactly the current session. Public transcript remains session-scoped by its existing key. Durable notes and P09 summaries are separate records whose producer identity, source session/range and mode visibility/memory provenance are explicit; the receiving mode policy selects them, with no raw cross-session fallback. Provider continuation IDs, retries, compaction cursors and opaque reasoning blocks inherit that session boundary. Ambiguous legacy private rows keep `NULL` and remain inspectable/exportable but do not enter any new session's raw context; durable journal evidence may associate only provable rows. A turn reloads one coherent topology snapshot before planning, pins it until settlement, and reconciles changed topology before publishing state. Dreams obtain a service-owned serialization lease spanning inference without holding SQL transaction/append lock; cancellation/death releases it. Promotion against a moved live base preserves the candidate and reports a typed conflict without rerunning inference.

P09 owns summary format and source-range provenance; P11 owns session create/fork/resume and public-prefix semantics; P08 owns private reasoning persistence. Those changes need this session ID contract before storage edits. P30 alone removes the conversation-driver lease and permits simultaneous sessions. Reject a namespace-only session suffix: it obscures legacy attribution and makes policy/query/export audits harder. Reject a shared project actor log: it would interleave unrelated concurrent conversations.

## Operational surface

The listener is a checked local Unix socket or private Windows named pipe; it has no TCP bind address, container service, installer registration or environment secret. The ordinary `kuru` executable starts it from the same verified binary image, so version and architecture match the client at cold start; a separately updated binary must negotiate with an already-running service. The endpoint record and temporary connection secret live only in owner-private state outside the tool root and are removed after verified shutdown. Request frames have a 100 MiB cap so the existing 16 MiB typed-message limit survives JSON escaping, with a 128 MiB shared permit budget acquired before payload allocation; handshake frames are smaller and partial frames have deadlines. Keep bulk writes server-side and export paged so callers do not incur an IPC roundtrip per row; cap replies at the same frame limit. The CLI reports startup, attachment, incompatible version and idle cleanup through fixed diagnostic text, without printing secrets. Packaged Windows, macOS and Linux paths use the same internal entry and existing embedded engine.

## Integration contract

`kuru-memory` owns endpoint election, authenticated attachment, typed store operations and the backend `MemoryStore`; `kuru-platform` owns only OS-specific socket/pipe, process and checked file mechanics. Runtime and CLI continue using the existing memory API through a client facade and never receive raw Dolt credentials, SQL pools or general SQL execution. Frame envelopes contain protocol version, service generation, bounded request ID and a typed operation; replies carry exact result or a fixed typed failure. Session IDs are opaque canonical strings defined by the existing session contract; P29 validates them at raw-history writes and query boundaries. Store schema version, protocol version and store instance are separate handshake fields. Existing `kuru-memory` real-Dolt fixtures form the compatibility baseline; new multi-process fixtures run the same service entrypoint as the packaged app. CLI flags and config parsing remain owned by the separate config lane; this change touches only internal entry dispatch and memory open/close integration.

## Risks / Trade-offs

- **[Service transport breadth]** → Implement typed, bounded operations against the existing `MemoryStore` API, keep service-only SQL handles and prove full runtime path in native fixtures before migrating direct callers.
- **[Starter/service shutdown race]** → Election lock, generation handshake and operation permits make reconnect atomic with idle shutdown; crash fixtures verify one owner.
- **[Old binary/schema mismatch]** → Negotiate explicitly and leave an active incompatible service untouched; keep schema, protocol and store-instance versions distinct.
- **[Windows private IPC/process inheritance]** → Use `kuru-platform` safe owned process and pipe APIs, audit legacy spawn call sites, and test native ACLs, EOF and cleanup.
- **[Concurrent writers before P29]** → Retain the CLI conversation lease until history isolation and mode-policy tests pass; service attachment itself does not relax that lease.
