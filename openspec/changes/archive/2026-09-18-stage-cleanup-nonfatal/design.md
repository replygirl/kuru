## Context

`provision_with_extractor_observed` (`provision.rs:110`) extracts into a disposable private stage `versions/.install-<rand>/private` (`provision.rs:135`, `files.rs:295`), probes it, then publishes `versions/<target>`. On success `StagedActivation::finish_published` (`provision.rs:588`) drops the candidate and probe handles and calls `PrivateTemp::close` (`files.rs:327`); its failure is returned as `Err` and surfaces from `MemoryStore::open` (`store.rs:728`) as a hard CLI failure. On Windows, `close` runs a bounded reconcile window of `CLEANUP_RETRY_LIMIT = 2 s` (`files.rs:359`, `files.rs:626-654`); a native holder of the just-executed probe image can outlive it, so an engine that was published and verified is reported as a failed open.

The abandoned-activation path already models the correct disposition: `StagedActivation::retain` (`provision.rs:604`) calls `PrivateTemp::keep` (`files.rs:321`), which disarms cleanup and deliberately leaves the stage on disk. Nothing then collects it: no sweep of `versions/` exists anywhere in the workspace, and a warm open never enumerates `versions/` — `CheckedCache::open_and_verify` (`provision.rs:239`) opens only `versions/<target>` and `Directory::revalidate` (`kuru-platform/src/fs.rs:386`) walks the named ancestor chain by identity. So a leftover stage is invisible to later opens, which makes non-fatal cleanup safe but makes an unswept leftover a silent disk leak. The report-only change and the sweep therefore ship together.

## Goals / Non-Goals

**Goals:** Post-publication stage removal becomes report-and-continue; the leftover is receipted so it can never be confused with a live engine and can be collected later; a bounded sweep under the existing installation lock reclaims receipted stages; one honest stderr line and one diagnostics record surface the event.

**Non-Goals:** No change to publication outcomes or their exactness, no widening of the two-second bound, no deletion of a stage whose removal is uncertain, no forced deletion or PID/lock-based termination, no new configuration key, no new crate, no background thread, no model-visible or memory-stored record.

## Decisions

**Non-fatal completion.** `PrivateTemp` gains `close_or_keep` (`files.rs`, alongside `close` at `files.rs:327`): it captures the outer stage path and the private child path, runs the existing `close` body unchanged, and on failure returns a typed `StageCleanupFailure { stage, private, cause }`. Both platforms already leave the directory on disk at that point — the Windows branch has already called `_container.keep()` (`files.rs:334`) and `tempfile::TempDir::close` disarms its own drop — so no second removal is attempted, matching `retain`'s disposition exactly. `finish_published` returns `Result<Option<StageCleanupReport>>`; `activate_staged_with` (`provision.rs:660`) and `activate_staged_after_probe` (`provision.rs:634`) thread that value, and the caller at `provision.rs:170` handles it. Failure paths (`retain`) are untouched: an activation that did not publish still fails. Rejected publication stays rejected and uncertain-retained stays retained because nothing on those paths changes.

**Typed report.** `StageCleanupReport { stage: PathBuf, private: PathBuf, engine_version: &'static str, target: &'static str, executable_sha256: String, published: true, first_cause: String, os_error: Option<i32>, attempts: Option<u32>, elapsed: Option<Duration> }`. `attempts`/`elapsed` come from a new typed `StageCleanupExhausted { attempts, elapsed }` error carried as the context in `wait_for_cleanup_retry` (`files.rs:632-654`) — its rendered message is unchanged; the report downcasts the chain and records `None` when the cause is not the bounded exhaustion (the non-Windows path). `os_error` is the first `io::Error` raw code in the chain. Alternative rejected: parsing the formatted message.

**Receipt.** One small JSON file per leftover at `versions/.leftovers/<stage-dir-name>.json`, the directory created with `files::ensure_private_directory` (`files.rs:41`) and written with `files::write` (`files.rs:102`), which already stages and publishes atomically through `Directory::publish_file`. Fields: `{"version":1,"stage","private","engine_version","target","executable_sha256","published":true,"first_cause","os_error","attempts","elapsed_ms","recorded_at"}`. The receipt is the sweep's only authority: a stage with a receipt is collected, never opened for verification or execution. That rule is structural — no code path opens `.install-*` other than the sweep's removal, and the sweep only ever removes. Alternative rejected: a marker file inside the stage (it would require opening the stage we just failed to touch).

**Sweep.** `sweep_leftover_stages(versions: &Path, _lock: &CacheLock)` takes `&CacheLock` so the type proves the exclusive installation lock (`provision.rs:876`) is held. It lists `versions/.leftovers`, and for each receipt resolves `versions/<stage>`, requires the name to start with `.install-` and to be a directory, opens it `Privacy::OwnerOnly` / `NameRetention::Movable` and calls the existing `Directory::remove_tree` (`kuru-platform/src/fs.rs:491`), which revalidates identity and ancestors before deleting. On success, or when the stage is already absent, the receipt is removed. On any `RemovalError` — `Rejected` or `Uncertain` alike — the stage and its receipt are left for the next pass; no retry loop, no deletion on uncertainty, no PID or lock-name heuristic. Stages without a receipt are never touched, so an in-flight `.install-*` belonging to a live installer is out of scope by construction (and the lock already serializes `versions/` mutation).

**Sweep placement.** Cold path: immediately after `cache_lock` succeeds (`provision.rs:129`), before the new stage is created (`provision.rs:135`). Warm path: the early return at `provision.rs:124-127` would never sweep an already-published engine, which is the common case; so before it, one `symlink_metadata` on `versions/.leftovers` — absent in the normal case, which keeps warm opens lock-free — and only when receipts exist, a non-blocking `try_cache_lock` (the `cache_lock` body with `file.try_lock()` and `WouldBlock` returning `None` instead of waiting). A busy lock means an installer is active; the sweep is simply skipped.

**Cap.** `LEFTOVER_STAGE_CAP: usize = 8`, count-based and reporting-only: when the receipt count after a sweep reaches the cap, the report says so. It never deletes anything and never suppresses a receipt — dropping a receipt would orphan its stage permanently.

**Surfacing.** `MemoryOpenStage::RetainedInstallStage` is added (`progress.rs:10`); `MemoryOpenStage::bit` and `ProgressReporter::sent` widen from `u8` to `u16` and the channel capacity grows from 8 to 16 (`progress.rs:22`, `progress.rs:51`, `progress.rs:65`) because the eight existing bits are full. The stage carries no payload. `apps/kuru-tui/src/cli.rs` adds its label (`memory_open_label`, `cli.rs:370`) and, because progress lines are overwritten in a terminal, `MemoryProgressOutput::notice` — one retained `writeln!` on stderr emitted after `complete()` in `open_memory` (`cli.rs:384-421`), only on success. Stdout stays JSON-clean. The typed detail (path, cause, OS error, attempts, elapsed, digest, published-and-verified) goes to the diagnostics ring via one `tracing::warn!` with structured fields, collected by the ring layer (`apps/kuru-tui/src/diagnostics.rs:40`). Nothing is model-visible or written to memory.

## Risks / Trade-offs

[A leftover accumulates until the next cold provision or receipted warm open] → the warm-open sweep is exactly what closes that gap; the cap makes unswept growth visible rather than silent, and `docs/memory.md` states it.

[A stage that is permanently unremovable keeps its receipt forever] → intended: never delete on uncertainty. It costs one small file and one bounded directory listing per sweep, and it stays reported.

[Warm opens gain work] → one `symlink_metadata` when no receipts exist, which is the normal case; the lock is attempted only when a receipt file is present, and never blocks.

[Widening the progress bitmask could let a future stage synthesize a success line] → `Ready` remains the only completion signal and `open_memory`'s `debug_assert!(observed_ready, …)` (`cli.rs:411`) is unchanged.

## Operational surface

Windows memory-runtime CI stops failing cold installs on a post-publication holder. No bundled asset, secret, binary version, network route, CI topology, or configuration key changes. The published engine bytes, digests and identity checks are untouched.
