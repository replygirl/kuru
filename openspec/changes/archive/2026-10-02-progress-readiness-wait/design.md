# Design

The approved research design, with its critique and revision, is `tmp/roadmap/progress-readiness-wait-design-2026-10-02.md` (review base `b9453c5b`); its line citations are the review evidence for the site audit and the code facts below. This file records how the lead decided its open decisions on 2026-10-02 and the shapes the implementation commits to. Where the two differ, this file and the lead's decisions win.

## Context

- One client deadline, `started + startup_timeout_secs` (`packages/kuru-memory/src/service.rs:541-542`), covers election, the previous-owner probe and the readiness poll loop (`service.rs:690-709`). The loop reads its owner's activity record only for an observed open and only after its deadline check (`service.rs:712-720`), so the record can never extend the wait.
- A tokened owner already publishes its stages (format 1) on its own task (`service/activity.rs:341-368`) and retires the record by rename then removal before its store closes, both on a failed open (`activity.rs:508-514`) and in close (`service.rs:1698-1707`). Owner stderr is discarded in the product (`service.rs:1004`; Windows `Stdio::Null`), so the owner's failure reason never reaches the user today.
- A failed open reaps its started engine inside the open through one function, `close_failed_open` (`store.rs:4717`, called at `store.rs:2072`, `:2091`, `:2116`, `:2132`, `:7849`), bounded only by the supervisor reap allowance of about 13 s (`server.rs:62-72`). During that reap the record is present and unchanged.
- One published stage, `OpeningDatabase`, spans the fresh-store build, every engine start and validation, so stage changes alone would not have rescued the catalogued Windows rows.

## Goals / Non-Goals

**Goals:** the shapes below; nothing in the proposal or the spec delta is restated.

**Non-Goals:** making any owner phase cheaper; progress-aware election, previous-owner or inspection waits; owner-side bounds (engine start, project startup lock, cache lock); the gated open timeline and its stream; `KURU_OPEN_MARKERS`; the five progress sentences and a sign-of-life indicator (follow-on, recorded in `tmp/roadmap/dx-followons.md`).

## Decisions

- **D1 (a): accept the second-starter asymmetry.** A second concurrent starter keeps the flat election deadline (`service.rs:565-568`), so with an owner slower than one window the first starter now succeeds and the second fails with `memory service election deadline exceeded`, where today both fail. The spec carries it as "Second starter during a slow owner start". Rejected: a progress-aware election wait, which needs the second client to read the first starter's record, against the rule that a client presents only its own owner's record.
- **D2 (d): retirement observed, plus a failing mark with its reason, now.** The client fails at once when a record it has read is gone (`NotFound` on open) before it attached, and at once when the record it reads carries `"failing": true`. The owner sets the mark, with the error's text as a bounded reason in the same record, immediately before every close of an engine it started for a failure that the open then returns, after an audit that each such `Err` always propagates out of the open (verification 3.4): one call at the head of `close_failed_open` covers its six callers, and the same mark precedes the engine-start reap (`startup_failure`), the migration, candidate-recovery and stage-session workers' failure closes, the template build's failure close, the usage-ledger failure close and the read-only version refusal. The reason lands in this change with the mark. The publisher replaces the starter token's spellings and the tag in it, and a mark set through the open's `Server` replaces both connection secrets of the store's identity; at `startup_failure`, before any `Server` exists, the reason is the start's own error text. Rejected: exit only (the reap after a failure is bounded by about 13 s, not small against a 1 s window); a `"failed"` field written after reordering retirement after close (changes the specified retirement order and still misses failures that reap inside the open); retirement alone (leaves a failure reaping inside the open reported as a stall, without its cause). If the reason proves larger than the mark itself, the mark lands in this change and the reason becomes the next change, and the PR body says which.
- **D2 addendum (2026-10-02, after PR #174's first CI run): the mark also covers an owner that ends after its store opened and before its starter attached.** Evidence (**measured**): run 37004105273, job 110828480946 (ubuntu-latest coverage partition 6), `cli_supports_all_modes_model_discovery_persistent_sessions_and_dreaming`, step `["run", "plain answer"]`: an ownership wait, a service start, then `memory service ended its open before readiness; owner progress: last=OpeningDatabase advances=29 since-progress=33ms`. Diagnosis and critique: `tmp/roadmap/pr174-owner-retired-race-2026-10-02.md`. It was not a race. A healthy owner cannot make its record absent before its starter attaches, for these reasons. The record's name is replaced only by a staged `renameat` over it. Retirement has three tag-checked sites. Every start mints a fresh token. Close runs only after the serve loop returns, and that needs one of: the starter's admission, the 30 s starter deadline, a lock-verify error or a non-timeout accept error. Two exclusions complete that argument. `retirement.requested()` needs `RetireIfIdle`, which only `request_idle_retirement` sends; its only product caller is maintenance, which holds the Start lock that the starter holds throughout its wait. `ServiceLock::release` verifies and unlocks without unlinking the lock name, so a predecessor's release cannot fail the serve loop's `lock.verify()`. `OwnerRetired` was therefore a true report: the owner ended without serving, either in its post-open `prepared` arm (listener bind, `EndpointRecord::for_store`, endpoint publication) or on a serve error before its starter attached. Both paths retired the record with no mark, so the reason was lost. Decision: one function, `close_store_and_record`, orders both endings. (1) It marks the record failing under verified owner authority (`lock.verify()` immediately before, because this write, unlike tag-checked retirement, replaces whatever holds the name). The reason is the error's own text, with the store's identity secrets, the endpoint's connection secret, the token spellings and the tag replaced, and it is bounded. (2) `Publisher::mark_failing` joins the publisher and awaits that one write on the owner's own task, so no write can follow retirement. (3) It then closes the store and reaps Dolt. (4) It retires the record, whatever that close returns. If the authority check or the write fails, the record is retired before the close, as before, so the starter still fails at once. Awaiting the write adds no new kind of wait, because retirement already awaits the publisher join, including any write in flight, in that position. The in-open mark keeps "without delaying that close". A serve loop that ended on a lock-verify error is never marked. Rejected: (a) a client that concludes only after a later attach also misses, which changes no outcome because the endpoint always retires before the record; (b) a ready or retiring field, a format bump for a race that does not exist; an unawaited mark write, which would leave an unmarked record through a reap of up to about 13 s; any client wait, retry or longer bound. Residual: the underlying fault of the failed owner is still unidentified. The command-line `Sandbox` now passes every command `KURU_TEST_MEMORY_OWNER_DIAGNOSTIC`, so the next occurrence shows the owner's own error. A green fresh run is not evidence that the fault is gone. A second source of the same symptom, by design without a reason, was seen locally. In one full `//packages/kuru-memory:test` run on macOS arm64, `service::tests::a_client_racing_shutdown_elects_a_successor_without_error` failed with `racing client failed at AfterReap: memory service ended its open before readiness; owner progress: last=VerifyingRuntimeCache advances=11 since-progress=53ms`. That is a spawned successor whose open failed during runtime-cache verification, before any engine started; such a failure is not marked, because no reap would keep a mark visible. The test passed 3/3 alone and in a second full run. Its cause is unidentified, and the test's electing process is the test runner, so only a shell-set `KURU_TEST_MEMORY_OWNER_DIAGNOSTIC` can capture that owner's stderr. It can fail a fresh CI run and is a candidate for fixing at its cause. It does not move the CI failure off the post-open path: a pre-engine failure at 29 advances would need a cold open, and that step ran on a cache the test's earlier commands had warmed. Record keeping: the lead chose to amend this archived change rather than open a new one. The merged `project-memory-owner` spec and this change's delta now carry the same text for "Tagged open activity record" (extended mark and a new scenario) and "Attachment-bound idle cleanup" (its close-order sentence and the "Activity record retired before the store closes" scenario scoped). The second requirement is newly listed as MODIFIED here.
- **D3: land independently of `feat/readiness-owner-timeline`.** That branch is not on origin and this change uses none of it. Whichever lands second rebases the two readiness `bail!` sites and its T4 test; its extra stamp sites then become progress points through the milestone pairing below.
- **D4 (a): a test-support stand-in owner.** `service_entry` checks, before anything else and only under the `test-support` feature, `KURU_TEST_MEMORY_SERVICE_STAND_IN`, naming a release file. The stand-in takes no lock and writes nothing; it polls for that file every 10 ms of real time in its own fixture process (precedent: `client_fixture_entry`) under a 120 s bound and exits with the decimal status the file holds. The test passes the variable only through the task-local owner environment (`activity::with_owner_environment`), which both platforms' spawns apply, and the executable is the prepared `test-support` snapshot (`crate::store::test_supervisor()`). The four readiness tests therefore run on Linux, macOS and Windows; stdin cannot be the seam because it is null on both platforms. Rejected: keeping the tests `cfg(unix)` with the shell stand-in and recording a Windows gap.
- **D5: format 2 only.** The record is `{"format":2,"tag":"<64 hex>","stages":[…],"progress":<u64>}` plus, only on a failing open, `"failing":true` and `"reason":"<text>"`; still `deny_unknown_fields` and 4 KiB. Format 1 is not accepted. The owner is always the client's own executable, so a mismatch arises only when that binary is replaced in place between a client's start and its spawn: a pre-change client meeting format 2 shows only its own stages and keeps its flat wait, and an updated client that spawns a pre-change owner reads no usable record and waits one window from spawn, today's behaviour. Both directions go into `docs/release.md`. Rejected: also accepting format 1, a decode path reachable only by an in-place replacement.
- **Per-open counter.** `MemoryStore::open_observed` creates one counter per open (an `Arc` watch sender advanced by a synchronous `send_modify`), carried on the open's `ProgressReporter` and on its `ServerOptions`, so engine starts and creation workers advance their own open's count. Rejected: a process-global counter, because in-process test owners run concurrently and would advance each other's records.
- **Progress points.** Every `report` call, including a deduplicated repeat; every `open_timeline` milestone stamped inside the open, paired at the site as stamp-and-advance; every 8 MiB copied by extraction or hashed by warm verification; every completed migration step. The design's audited non-sites (the supervisor's port retry, the pool acquire loop, the project startup lock wait after its one report, the test hold loop) carry no advance.
- **Publisher spacing.** A stage change is written at once; a progress-only change is coalesced and written at most every 250 ms with a trailing-edge flush, so the last advance before a stall always reaches the record. Rejected: 100 ms, which on a slow Windows disk spends ten synced writes per second against the extraction being reported.
- **Client loop.** Per poll: attach, then `try_wait`, then one bounded read of the own record, then the window check, then the poll hook and the 10 ms sleep. Change detection compares `(stages, progress, failing)` with the last record read rather than testing for an increase, so a stale same-tag record (possible only with an explicit test token) counts once and cannot hide a new owner's first advances. A stale same-tag record that carries the failing mark would end a new owner's wait at once; that too is reachable only with an explicit test token. The failing mark is not progress: `OwnerFailed` reports the time since the change before it. `Absent` also covers a missing services directory, which is never removed once created, so it is absent only before the owner's first write. The client state lives in `activity::OwnerWatch`; every starter reads its own record whether or not its open is observed, and only an observed open is forwarded stages. `Absent` is only `NotFound` on opening the name; a failed post-read verify, a foreign tag or a decode failure is `Unusable` and moves nothing. `ReadinessFailure` is a `std::error::Error` returned through `anyhow`, so tests downcast rather than parse; the `owner progress:` clause follows the leading text and precedes any test observations and the client phase split, so the existing split parser keeps working.

## Risks / Trade-offs

- [A site that loops without reaching a new point advances] → the site audit is a task with file:line evidence; no advance in a sleep, retry or lock wait.
- [Harness bounds sized for one window now surface a slow-but-advancing owner as a harness timeout] → kept: that is real slowness to report.
- [A1 masking: a single engine start longer than the window still fails] → said in the docs and the spec; the A1 phase-2 work remains and must not count this change as its fix.
- [The retirement signal depends on the record never leaving its name except at retirement] → the spec requires the publisher to replace only by publishing a staged record over the name.
- [R1's real listener and pipe handshake on Windows after the clock resumes has only run on Unix in the cadence test] → R1 keeps that path on all platforms; if Windows CI shows its accept does not complete, R1 ends on Windows by releasing the stand-in at the same poll and asserting `memory service exited before readiness`, which still proves three windows were waited, and the ledger records it.

## Operational surface

- **Interactive surface:** the CLI and TUI open path. A command waits longer for a slow owner that keeps progressing, and its failure now carries one of the four leading texts with an `owner progress:` clause; the five progress sentences, `KURU_OPEN_MARKERS` and JSON-on-stdout are unchanged.
- **Bind address and transport:** unchanged; the owner's private Unix socket or named pipe and its endpoint record are untouched.
- **Container versus runner:** none; the owner is a local child of the user's own command on Linux, macOS and Windows.
- **Required secrets:** none added. The record carries a derived tag, never the starter token or connection secret; the failure reason is the owner's own error text.
- **Connection limits:** unchanged (`MAX_ATTACHMENTS` 32). The start lock may be held for several windows while the owner progresses; a second starter waits within one window.
- **Binary versions and architectures:** one binary is both client and owner; a mismatch arises only from an in-place replacement between a client's start and its spawn, and both directions are documented in `docs/release.md`. No architecture-specific code beyond the existing Windows owner environment, through which the test-only stand-in variable passes like the other test hooks.
