## Context

`operations(id, label)` is branch-local and indexed by its UUID primary key. Ordinary store and usage-ledger writes generate a server UUID, insert one receipt in the Dolt transaction, and delete the previous row. `resolve_uncertain` waits for the original SQL session to end before checking that row. A service request currently has an unrelated wire UUID, so losing its reply leaves no stable query key after another writer commits. The living `versioned-memory` spec also requires sole-receipt replacement; its requirement must change for upgraded writable views while historical branch preservation remains exact.

## Goals / Non-Goals

**Goals:** Query an exact accepted mutation across sibling writes and owner restart, bind exact retries to the same work, and preserve branch-specific candidate and ledger results. A missing receipt means noncommit only after original work cannot still settle.

**Non-Goals:** A second event journal, duplicate private request bodies, automatic replay after a broken transport, conversion of legacy receipts into fabricated request IDs, or concurrent conversation admission.

## Decisions

1. **Extend the indexed receipt, not the SQL log.** Migrate the existing `operations` table to a current format with a compact receipt version, method/view/request SHA-256 fingerprint and bounded result reference beside the existing UUID primary key. Preserve old rows with a legacy format and no invented fingerprint. Current-schema writable transactions append a row instead of deleting predecessors, so a later sibling write cannot erase the query proof. For receipt-bearing unit writes, the durable idempotency key is `(store instance, pinned branch/view, logical UUID)`: reject a repeated key with different method or arguments, but do not claim global UUID uniqueness across branch-local tables. Dolt candidates inherit main's receipt rows, so the physical UUID primary key for a new request is deterministically derived from the persisted, Dolt-verified store instance UUID, exact pinned branch name and caller logical UUID with length-tagged domain separation. An inherited main row cannot alias the same caller UUID on a candidate; a promoted candidate row keeps its original view-derived physical key in main. An outcome query must carry the original view and never treat a receipt on another view as its own. The caller creates one logical mutation UUID before transmission and retains it across the attempt, outcome query and any explicitly authorized exact unit-write retry; the wire correlation ID may be separate. Fingerprint canonical encoded arguments together with operation kind and pinned branch/view identity, without storing a payload copy. Rejected: searching unbounded `dolt_log` on every uncertain reply or adding a parallel request journal.

2. **Upgrade only writable branches under owned lifecycle authority.** Add one immutable main schema migration; old binaries reject its newer version. The permanent usage branch remains independently writable, so stage its matching receipt-shape upgrade at an exact clean base and publish only by checked fast-forward before ledger writes. Reconcile a lost DDL or publication reply using the existing migration/candidate branch-ref discipline. New candidates created after main upgrade inherit the current shape. Existing pre-upgrade candidate names, heads, rows and branch-local schemas remain unchanged and readable through their historical validator; their old base is stale against upgraded main, so they cannot promote or become writable current views. Rejected: migrating historical candidates in place or letting a usage writer fall back to `DELETE FROM operations`.

3. **An outcome query is branch-aware and waits for acceptance to settle.** The owner tracks in-flight logical mutation IDs and serializes short writes. `Outcome(id, original view, fingerprint)` returns one of in-flight, committed with a matching typed result, definitively absent, or still uncertain. It checks the original branch's indexed receipt, or a receipt reachable after checked promotion, only after the handler finished its owned worker; after owner crash it waits for verified supervisor/Dolt reap and branch recovery first. A missing row while a worker or native publication may still complete is never noncommit. A candidate view whose exact ref has been explicitly abandoned and reclaimed is also indeterminate from its missing row: that absence cannot erase proof of a write which may earlier have committed privately. The client fences all clones, candidate and ledger handles after cancellation or incomplete mutating reply and resolves the same ID through a newly authenticated generation; it never sends the mutation again by itself. A definite authenticated rejection does not poison the session. Rejected: reconnecting with a new UUID and treating absence at an arbitrary instant as proof.

4. **Use domain result evidence.** Unit append, checkpoint, state and forget can resolve from their same-transaction compact receipt. A lost candidate unit-write reply also invalidates that attachment's candidate handle: after proving the exact indexed receipt, the client must query the original creation UUID for the exact still-open ref and return a fresh checked candidate handle before releasing its mutation fence. Generic Boolean reconciliation cannot silently release that fence while leaving the candidate unusable. Usage admit/observe/settle already persist invocation-keyed records; outcome validation checks those natural keys and their exact value, without another private copy. Candidate creation derives its exact Kuru-owned branch ref from a caller-retained logical creation UUID before dispatch. A lost begin reply triggers only a read-only exact-ref outcome/reattach query, including after restart; the supported client never replays Begin. Missing or resolved refs do not cause recovery to create a new branch. Abandonment/promotion use that exact ref and base/target reconciliation to report a typed outcome or preserved conflict. An open conflict receives a fresh authenticated candidate handle from the original creation UUID before the client releases its mutation fence; a conflict already resolved by the inverse transition returns no candidate handle. If an unchanged candidate's refs have already been reclaimed, base and target are identical and the surviving history cannot distinguish a no-op transition from another resolution; report uncertainty instead of fabricating success. Attachment loss releases only connection handles and cannot abandon the branch. A retired-generation candidate handle is never returned as usable; a later generation may issue a new checked handle only for a provably retained candidate. Rejected: one generic applied Boolean for result-bearing branch operations.

## Risks / Trade-offs

- [Retained compact receipts grow with writes] → Keep only UUID, kind, digest and bounded result reference; account for their growth in operational documentation and never silently expire evidence still needed for no-replay recovery.
- [Permanent usage branch has an older schema than main] → Stage and verify its independent upgrade before admitting ledger mutations; leave any failure and old bytes inspectable.
- [A client can vanish before it receives its request ID] → Never infer that a fresh open resolves an unknown effect. Existing durable turn/invocation IDs supply stable exact-retry identity where available; caller-generated IDs without durable caller provenance remain fail-closed and require explicit inspection.
- [Candidate ref transition spans more than a row update] → Use existing exact ref/base-target reconciliation and keep unresolved candidates, instead of inventing a success bit.

## Operational surface

This is a checked local service and Dolt migration within the existing `kuru` executable. It adds no network bind address, container or runner, installed daemon, required secret or external service. The owner-private endpoint continues to use the current per-generation secret; request IDs and fingerprints are not credentials. Typed IPC keeps the existing 100 MiB per-frame and 128 MiB shared allocation budget, at most 32 service attachments, and bounded operation deadlines. A cold owner must reject an incompatible binary/schema rather than downgrade or replace a live older service. Native Windows, macOS and Linux jobs execute the same bundled target architecture and migration fixtures; cross-target compilation alone is not acceptance.

## Integration contract

`kuru-memory` owns the request-ID, receipt, branch migration, outcome and IPC encoding; `kuru-platform` remains unaware of storage methods. The public facade retains existing method names and adds internal logical-ID/outcome plumbing for callers with durable turn or invocation identity. An outcome key is the canonical UUID plus exact project/store instance and pinned branch/view identity; the fingerprint covers method and canonical arguments. The same UUID on another branch is a distinct scoped key and cannot prove the original view's outcome. The main branch's registered schema version, the independently pinned permanent usage branch and historical candidate versions are validated separately. Real-Dolt native fixtures send typed requests through the service entry, with dropped replies, sibling writes and owner restart. This prerequisite lands the internal facade and typed client, but leaves ordinary CLI writable opens on their existing local path. The dependent `project-memory-service` change performs the normal CLI switch only after runtime candidate write and publication recovery use the typed results; no raw SQL or private body enters a reply.
