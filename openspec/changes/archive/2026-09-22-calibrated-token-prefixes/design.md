## Context

The connector already serializes the selected Responses body before its context check, but core currently divides its byte length by two. The catalog knows route/model limits, while the runtime puts actor identity and changing public context before common rules. Reported cached tokens are stored with a missing-versus-zero distinction. The canonical P07 plan calls for calibrated estimation and shared prefixes, not an online counting dependency.

## Goals / Non-Goals

**Goals:** Keep the context decision attached to the bytes that will actually be sent; distinguish a sourced tokenizer estimate from an unknown-route fallback; make common prompt material byte-identical where intended; provide reproducible request-shape and real reported-usage calibration evidence.

**Non-Goals:** An exact token count for the Responses envelope, an implicit cache breakpoint, a per-invocation token-count API call, a new credential route, a model-availability claim from tokenizer metadata, or a subscription cache guarantee.

## Decisions

1. **Tokenization eligibility is a route/model fact.** A validated catalog record may carry an encoding only for a supported real model ID and route, with upstream source and checked version/date. OpenAI's [`tiktoken` commit `212b893ba940cba53476851103d2e5c1d0020c6e`](https://github.com/openai/tiktoken/commit/212b893ba940cba53476851103d2e5c1d0020c6e) changes the `gpt-5` family mapping to `o200k_base` so it covers catalog-supported GPT-5.6 IDs; its permissive prefix lookup does not make arbitrary matching IDs available or validate their limits. The current evidence does not map `gpt-6-astra`, so that model retains fallback. Custom API bases and unknown provider IDs never inherit OpenAI's mapping by spelling. An open-ended library `encoding_for_model` call was rejected because it could silently assign future or fictional IDs.

2. **Count the final selected body locally, with an explicit error margin.** The connector measures its final serialized body after tool, effort, message and native-continuation selection. For an eligible text request, it uses the pinned `o200k_base` tokenizer on the actual serialized text and a documented structural allowance derived from the final body's item/tool count; the result is labelled a tokenizer-derived estimate, not an exact provider count. When Kuru saves native output for a tool continuation, it retains the exact output-item ranges across successive pending hops. A sizing-only copy removes all those ranges, tokenizes the remaining serialized body, and adds the earlier bytes/2 heuristic for the removed serialized byte delta plus the structural allowance. The actual request retains every native byte; the mixed estimate is labelled and makes no assumption about encrypted-field format. Unknown/custom routes retain the historical bytes/2 heuristic plus the modest allowance, avoiding a blanket context reduction without evidence. Neither byte heuristic is an upper bound. A byte-only estimator for all supported text was rejected because multilingual, code and JSON punctuation deviate materially from a single bytes/token ratio. The transport's 2 MiB check remains separate. The estimated fit check still refuses before dispatch when mandatory material plus output reserve does not fit.

3. **Calibrate without adding an inference roundtrip.** Check tokenizer vectors against pinned upstream examples. Record measured error by request class against genuinely reported usage or an authorized offline official `/v1/responses/input_tokens` count; synthetic fixture usage validates plumbing only and must not be called calibration. Keep versioned, content-free or artificial request-shape fixtures and aggregate error numbers in verification/docs. Runtime inference never calls the count endpoint, including near the boundary. If a count is unavailable, the documented margin/fallback remains in force and the check is labelled unverified rather than exact. This avoids new latency, credential requirements and failure modes.

4. **Build the shared prefix before actor-specific material.** In the existing `instructions` field, put stable Kuru mode rules and reviewed project instructions first, then actor identity, phase, current topology and mutable public transcript. Keep actor-private history and native continuation in their existing actor-scoped message/pending fields. Tool schemas remain deterministically ordered and are compared as part of the actual serialized request shape; do not insert a cache marker unsupported by either route. Provider cache ordering is semantic; JSON object-key serialization order is not a cache-prefix contract. Moving private material into a global shared prefix was rejected because it would cross actor visibility boundaries.

5. **Measure reuse only from observations.** Compare the common instruction prefix and deterministic tool-schema projection of final serialized requests, along with their reported `cached_input_tokens`, preserving `None` versus `Some(0)`. Do not infer a cache hit from a matching projection, expected minimum length or API documentation for the `codex` subscription route. Continue to mark cache-write pricing unapplied where it is not represented in the frozen accounting basis. This avoids inventing cost savings.

## Risks / Trade-offs

- [Tokenizer and serialized envelope differ] → Label estimate provenance, retain structural margin, measure error against real usage and keep a conservative fallback; never call it exact.
- [A shared instruction prefix can change behavior] → Preserve all existing instructions and visibility, assert actor-specific content remains after common material, and exercise multi-actor request fixtures.
- [Tokenizer assets increase binary size and startup work] → Pin one embedded encoding, initialize it once, document its license and measure request sizing time; no runtime asset download.
- [An overly conservative margin omits optional history] → Calibrate on multilingual, code, tool-heavy and continuation cases; document error and adjust only with measured evidence.

## Operational surface

This changes the existing local `kuru` process only: no bind address, container, new secret or runtime service is added. The tokenizer asset is embedded in the ordinary executable for every supported target, pinned with its Rust crate and license, and initialized once through the library's singleton. Each mapped request tokenizes the final bounded JSON once; mixed native requests also clone and serialize a sizing-only copy, adding bounded per-request CPU and allocation relative to bytes/2. Cold and warm costs were not separately timed. The direct API keeps `OPENAI_API_KEY`; the subscription route keeps its own native authentication. Offline calibration may use an already-authorized direct-API credential but runtime sizing never requires it. No remote token-count roundtrip or connection limit is introduced.

## Integration contract

`kuru-connectors` remains the owner of the final native Responses body and its context preflight; `kuru-core` supplies route/model eligibility and sizing provenance, while `kuru-runtime` supplies common and actor-scoped content. Native HTTP fixtures capture actual outgoing JSON and route identity, then compare selected bodies, source labels and reported usage. Supported model IDs and effort values come from live discovery; the catalog only enriches a matching route and ID with sourced encoding metadata. Custom Responses bases and unknown IDs keep fallback. Fixture usage fields match the existing typed `input_tokens`, `input_tokens_details.cached_tokens` and `output_tokens` shape; absent and zero remain distinct. No public wire schema or credential scope changes.
