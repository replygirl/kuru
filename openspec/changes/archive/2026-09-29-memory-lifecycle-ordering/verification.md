The independent check of round 11 found that its `.dolt` skip was global: any directory named `.dolt` anywhere under a fixture root went unread, where before round 11 the guard had read the first 8 levels inside it. **Ruling: narrow the skip.** The scan skips a directory named `.dolt` only when it is the database repository of a store the guard has already recognised, in the layout the product creates; every other `.dolt`, at any other position, is scanned like any other directory and is subject to both budgets. No product code changed; the change is `test_support/fixture_dir.rs`, `test_support/template.rs` (its tests module), `docs/development.md` and this record.

Layout, from the product: a store directory is `<data>/memory/<hash>` (`store.rs:7585`); its supervisor hands Dolt `data_dir` `<store>/data` (`server.rs:2161`, checked at `:1665` and `:2267`) and creates the one database `kuru` (`server.rs:2273`), so the repository is `<store>/data/kuru/.dolt`. A kept real root on this host shows exactly `data/.dolt` (empty), `data/kuru/.dolt` and, inside it, `stats/.dolt`. Skipping a recognised store's repository loses nothing the scan looks for: `lifecycle.lock` (`server.rs:1181`), `identity.json` (`:1898`, `:2319`), `endpoint.json` (`:1979`) and `server.log` (`:2032`) are in the store directory, whose entries the supervisor admits by name (`:1293-1303`); the owner lock is in `<data>/memory/locks` (`service.rs:1252-1257`); the Windows lease is in `<data>/memory/lifecycles` (`store/purge.rs:231`, taken at `server.rs:1183-1195`). The engine's own files in that repository are covered by the store's quiescence record, which a recognised store must have and which must still match, not by the scan.

Mechanism: the scan defers each directory in the position `<X>/data/kuru/.dolt` instead of reading it. Once the rest of the tree is read, it recognises stores from the lease files exactly as before, skips each deferred repository whose `X` is recognised and scans every other one under the same budgets and at its own depth, repeating while a scanned repository recognises further stores (recognition only grows, so no skipped repository could later need reading). An unkeyed store is not recognised, so its repository is scanned.

Fixtures the narrowed rule trips (corrected in round 14: a third, the packaged install and update acceptance in `apps/kuru-tui/tests/embedded_runtime.rs`, also tripped; kuru-tui was not built here, and CI found it): `test_support::template::tests::concurrent_processes_create_one_template` and `invalid_templates_are_rejected_and_rebuilt` (`first-green-attempt-template-fixtures-tripped.log`). Each keeps a template and unopened or partial copies, which carry `identity.json` without a lease and so are not recognised stores; their repositories are now read and reach 11 levels (`<name>/private/memory/<hash>/data/kuru/.dolt/stats/.dolt/noms/oldgen`; the kept roots held 140 and 321 entries). Resolved by the documented per-fixture remedy, a named budget at the call site: `TempDir::with_depth_budget(depth)` (which refuses to lower the default 8) and `TEMPLATE_FIXTURE_DEPTH = 11` in both fixtures. For those two roots the guard now reads every level of those repositories, where before round 11 it read 8 and stopped silently. Compared with the guard before round 11, every `.dolt` other than a recognised store's database repository is now read at least as far, and to the end or to a reported violation rather than a silent stop. The one deliberate exception, by the ruling, is a recognised store's `data/kuru/.dolt`: before round 11 its first 8 levels were read, and now none are, because nothing the scan looks for is written there and the store's quiescence record covers the engine's files.
