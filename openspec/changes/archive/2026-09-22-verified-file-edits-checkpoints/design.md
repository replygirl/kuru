## Context

`ToolHost` currently publishes `file_write` with a temporary rename and removes `file_delete` directly. Both already pass exact-file permission and checked project-root admission, but neither has a durable file-effect receipt. The app knows the private data directory; the connector does not. The existing platform `Directory` can retain file/directory identity and distinguish rejected from uncertain checked publication/removal. Runtime turn journals and provider call IDs supply stable admission identity, while direct CLI tool calls need their own one-shot identity.

## Goals / Non-Goals

**Goals:** one path for checked native file mutation and recoverable before/after evidence, with bounded private storage and a narrow selected-undo/prune surface. Keep permission, protected-path and nested-instruction replan ordering intact.

**Non-Goals:** a general transaction journal, workspace-wide snapshot, shell/MCP rollback, automatic checkpoint expiry, Git reset, or a memory/Dolt schema change.

## Decisions

1. **Admit a checkpoint store explicitly at the app boundary.** The app passes its checked private data directory and retained canonical root to a project-bound checkpoint store; write-capable native tools require it. A read-only host still works without the store. This avoids deriving a user data path inside connectors or placing recovery bytes beneath the tool root. Direct provider-free tool calls receive a fresh one-shot ID; runtime calls use the admitted session/turn/tool-call identity. Rejected: silently retaining the old uncheckpointed write path when the store is unavailable.

2. **Apply ordered exact-context hunks to one immutable captured file.** Each hunk identifies old bytes plus adjacent context and replacement bytes; every match must be unique, ordered and nonoverlapping in the same bounded source capture. Revalidate the held target identity and exact source bytes immediately before a checked atomic publication. Rejected: fuzzy patch placement and partial success after an earlier hunk.

3. **Use a narrow per-target recovery state machine.** Under one private project lock, reserve a bounded immutable receipt with before/after bytes, source/post hashes and expected target identity before touching the target. Create an empty owner-private sibling stage and, for creates, an empty ordinary access-policy template; bind their exact checked identities in the receipt before writing any staged payload. The stage directory shields bytes while the staged file receives the source's effective mode/DACL. If native owner/group differ between source and stage, refuse before publication rather than silently changing effective grants. Retain an opaque source access token (Unix owner/group/mode; Windows owner SID, effective DACL and protection bit), reject a detected change on the held source before publication, and classify a detected post-publication change as uncertain; this detects ordinary races without claiming an atomic lock against external ACL writers. Windows restores the source's protected/unprotected DACL behavior through the retained published file handle under its real parent before sealing `applied`; failure after publication remains `uncertain`. A successful checked publication/removal advances the receipt to `applied` while the destination handle remains held; an interrupted or uncertain result leaves it `prepared`/`uncertain`. After process loss, matching destination bytes or a serialized file ID alone cannot prove Kuru published a prepared create/replace, just as pathname absence cannot prove its delete; those records stay unresolved and cannot authorize automatic retry or undo. A repeated logical ID with changed operation or arguments conflicts; an exact repeat inspects the receipt and never blindly republishes. The receipt is a file-recovery record, not a second general operation ledger. The private project store has an individual 2 MiB snapshot ceiling, a 128 MiB total ceiling, and a 10,000-file inventory ceiling; counting includes worst-case settlement growth and conservative retained-stage reservations. Rejected: putting snapshots in Dolt history or deleting old receipts automatically to make room.

4. **Treat delete absence conservatively.** A completed, verified `remove_file` can mark a receipt applied. After a crash before that marker, absence alone cannot show whether Kuru or a user removed the file, so the record remains unresolved and cannot authorize automatic restoration. A checked unchanged original target can settle as no effect; changed state conflicts. Bounded inspection shows the status and target state. Ordinary prune accepts settled records; explicit `--discard-uncertain` accepts one inactive unresolved record under the project lock and states that recovery/undo is forfeited. It removes only staging artifacts whose durable identities still match the receipt, refusing substituted names. Rejected: inferring an accepted delete from pathname absence.

5. **Undo only the selected settled edit.** A durably `applied` receipt remains usable after process restart: the undo handler reopens the current target through checked handles and rechecks the project root, exact file permission/protected-path policy, and expected post-edit bytes. It reserves an undo receipt before publication, then restores the before state through the same checked path. The original publication handle need not survive for this new, separately authorized undo. A mismatch reports conflict and leaves user bytes and recovery records intact. CLI/TUI expose inspect, selected undo and selected prune only, separate from dream undo. Rejected: a global rewind or automatically choosing the most recent file edit.

## Operational surface

This change opens no bind address, container service or external connection. The ordinary packaged Kuru binary remains the runner on each supported OS. It needs the existing checked canonical project root and an owner-private data directory; no new secret or native binary is required. One project checkpoint lock serializes its small local receipt inventory and mutation admission. Provider calls remain in the actor runtime, while the checkpoint store never receives provider credentials or becomes an MCP/tool root.

## Integration contract

The app owns the private data-dir path and constructs the project-bound store with the retained root identity. The connector owns native file target admission and consumes a typed operation identity from the runtime's settled session/turn/tool-call IDs; direct CLI calls use a one-shot ID. The platform supplies retained file identities and checked publication/removal. No SDK endpoint, route, mount or Dolt schema is added. A receipt's format version, canonical project binding, target path, operation ID, source/post hashes, byte lengths and state are validated together on reopen; unknown formats fail closed, and one logical ID with different arguments conflicts before an effect.

## Risks / Trade-offs

- [A crash falls between workspace publication and receipt settlement] → keep the prepared receipt, report the observed target state for inspection, and refuse a causal conclusion from matching bytes or a serialized identity after the held file handle has gone.
- [A user edits a target during an approval or before publication] → retain the checked target, compare the captured source immediately before publication and fail on changed bytes/identity.
- [Private snapshots are sensitive and can fill the data directory] → keep them outside the tool root in checked owner-private storage, cap each snapshot and the whole store, and require explicit pruning rather than silent expiry.
- [Filesystem publication and a private receipt are not one atomic filesystem transaction] → expose an unresolved status where exact post-state proof is unavailable, never claim guaranteed rollback from path absence, and make explicit discard the only way to forfeit such a record.
