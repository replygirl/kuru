## Context

The completed first slice captures root/ancestor instruction graphs and binds their exact bytes to one immutable `ConfigSnapshot`. `ToolHost` already validates native paths and applies exact permission decisions, including per-candidate decisions for bounded grep/glob. The runtime currently receives one instruction string, while the TUI's foreground review channel handles tool permission requests and the private workspace approval store holds one root-digest record. Nested discovery must join these boundaries without treating a tool grant as instruction trust.

## Goals / Non-Goals

**Goals:** Keep one checked configuration base, compose deterministic path-qualified instruction snapshots, review new prompt authority before effects/results, retain once and persistent choices, and settle pre-discovery mutations without replay.

**Non-Goals:** Eager scanning of the project tree, approval by filename alone, a new general command/skill registry, permission grants for sibling paths, or automatic retry of a model-authored mutation.

## Decisions

1. **Extend snapshots from captured sources.** Keep the initial `ConfigSnapshot` immutable and create a new immutable snapshot for a canonical sorted union of authorized target directories. The core cache retains exact base capture state and previously active nested source bytes/identities, so a later union never rereads earlier reviewed authority. Nested directories with no active source are not retained across calls; reusing one may discover a newly created source, which then requires review. This avoids retaining up to 10,000 empty search candidate directories on every long-running session. Capture traverses applicable nested directories in depth-then-normalized-path order, `AGENTS.md` before `CLAUDE.md`, expanding imports at their directive positions. Shared caps, deduplication and notices apply to the union; the manifest is rederived from its complete ordered active sources. A later invocation starts a fresh capture and sees changed files. Rejected: appending discovery-order text to the prompt or mutating the initially reviewed snapshot.

2. **Admission stays at the checked tool boundary.** Add an actor-only instruction gate to `ToolHost` after its existing exact permission decision and path revalidation. The connector derives instruction directories from checked project-relative targets: a file contributes its containing directory, while `file_list` contributes its checked directory itself. It never passes raw model path strings. Direct CLI tools pass no gate. For grep/glob, first gather the existing bounded candidate set and decide permission for every candidate; then submit only the allowed files' containing directories to the gate before emitting a path or reading matched content. Preserve search result order, hidden/ignore rules, and existing traversal/output bounds. Rejected: pre-discovering an entire requested search root or granting a subtree because the search tool itself was allowed.

3. **Refresh context explicitly and settle mutation once.** An actor tool outcome carries an optional reviewed instruction projection back to `Harness`, which installs it before the next provider request. If a write/delete first adds applicable instructions, `ToolHost` returns a typed replan-required result before the file effect; the runtime records the original call result and lets the next model continuation plan anew. Other calls from that same pre-discovery provider response also settle without effects. Read-only file/search calls can complete after review. Revalidate the checked target after any foreground wait; persist a reviewed grant only in the later publication step. Rejected: executing a stale model-authored mutation immediately after approval or silently replaying it.

4. **Reuse foreground review with a distinct trust decision.** The TUI presents the existing review overlay for a bounded redacted complete manifest and offers once, persist, or deny. A trust request is distinct from a permission request and cannot write tool grants. The app-owned gate checks the existing approval store, passes a pending request through the foreground turn channel when available, and publishes the new instruction snapshot only after an applicable grant. Headless turns fail promptly with an actionable trust-required result unless their explicit invocation-only grant applies. Rejected: unconditional failure/restart in an interactive turn or treating `ApprovalSender` permission approval as workspace trust.

5. **Evolve one atomic approval record.** The existing checked root-digest JSON file becomes strict store schema v2 with a `base` complete approval, a bounded collection of nested complete approvals, and a fresh random generation on every publication. A v1 file is read as its original base plus an empty collection; an old binary rejects v2 rather than granting authority. Each nested entry stores a canonical sorted set of active nested source path digests and the complete extended manifest schema/digest/sorted claim digests, root identity, and approval method; no instruction content or raw path is stored. Root-only startup checks only `base`; path activation matches both the current source set and complete manifest. Persistent writes take the same root lock, reread the record under it, compare the pre-review generation (or checked legacy file-object identity), and atomically publish one updated file. An unchanged base preserves existing nested entries; a stale base can be replaced only as part of an explicit complete-manifest review, which clears the old nested entries. A nested review begun against an existing record never treats its deletion as permission to recreate that record; deletion or replacement makes it stale. A genuinely new persistent approval begun from absent state may create the base and nested entry only after explicit full-manifest review. Ordinary `trust revoke` still physically removes the one record and therefore all grants; an absent-record revoke creates nothing. The entry count and serialized bytes are bounded; exhaustion is reported and a once choice remains. A checked but invalid record permits a one-time choice; persistent review remains unavailable until that unsafe state is revoked or repaired. Rejected: a second supplemental approval file, which makes revocation and crash reconciliation non-atomic, or replacing the base with a nested manifest, which would make the next root-only startup stale.

## Risks / Trade-offs

- [A tool waits for both permission and workspace trust] → Keep them distinct and ordered; no path effect or result is released between decisions, and a denied permission target never enters instruction capture.
- [A source changes while a foreground review is open] → The current turn uses only its captured checked bytes and revalidates the retained root, target, and active nested directory identities before publication; a replaced directory cannot receive an approval for the prior directory. A later invocation computes a new digest. Compare the approval-store generation under lock before a persistent update.
- [Many search paths or nested scopes enlarge capture and private approvals] → Use the existing candidate cap, global instruction caps, fixed approval entry/byte limits and explicit omission/error notices; never silently truncate authority.
- [A native diagnostic PR can change the shared base while this slice is in progress] → Keep this change in its own dependent worktree and integrate/review onto the final prerequisite heads before delivery.

## Operational surface

Nested capture and review run inside the existing `kuru` CLI/TUI process. This change adds no bind address, container, installed service, network credential, connection pool, or platform binary; it uses the existing checked workspace and private approval directory. The ordinary executable and native target architectures remain those already supported by the repository. Foreground review is bounded by the existing turn lifecycle, and a closed channel or headless command fails promptly instead of waiting for a connection.
