# Design

## Context

The proposal and capability deltas define M1 scope. Clean N4 `421a15b9` provides distinct session claims, canonical native session/maintenance exclusion, expected-existing recovery, short owner write guards and immediate zero-client retirement. The existing active export is an application projection, not a native dataset image. The preserved P20 backup module supplies useful private inventory and absent-directory publication seams, but its schema-8/Dolt-2.3.3 equality checks, incomplete native validation and prefix-only output reads cannot be carried forward unchanged.

Pinned Dolt 2.3.5 `actions.SyncRoots` captures a dataset root for the pull/commit path; its clone fast path can select its own later source root, and a source-root read error returns nil. `dolt_backup.go` closes the destination and treats up-to-date as success. The completed destination is consequently authoritative. Pinned `fsck.go` reopens without the normal cached/self-healing path, scans every chunk, walks branch/tag/internal commit refs and validates their reachable trees. Its raw-ref walker skips working sets. These observations come from the exact `v2.3.5` upstream sources, not a generic SQL-success assumption.

## Goals / Non-Goals

**Goals:** Use native root copying and validation, preserve historical data without transferring live authority, and reuse existing checked filesystem, schema and lifecycle machinery. Keep source writes independent during backup and keep exclusive restore ownership concrete through all exits.

**Non-Goals:** No custom Dolt graph reader, schema/index addition, named backup catalog, replication/history-expiry policy, namespace rewrite framework, durable driver capability, pin change, engine download, provider loop or new scheduler. Preserve the old dirty P20 worktree; selectively adapt its useful functions only after this change's actual gate.

## Decisions

### Capture through the existing owner, validate the completed image separately

Add a typed `ServiceCall::Backup { target }` with a bounded completion result to the existing facade/service. Remote capture uses a dedicated same-generation attached exchange so ordinary calls/driver presence remain independent. The owning store opens one dedicated SQL connection, retains its checked connection ID and calls `DOLT_BACKUP('sync-url', file_url)` into a fresh private stage. No `Shared.write` guard, ordinary SQL transaction, native session writer lock or `MaintenancePermit` spans copying.

After actual query completion, native validation works on an independently restored private copy. Manifest metadata is read from that copy/image cut, never from then-current live rows. The ref inventory records actual branch heads/dirty working-set observations, tags and remote refs, with usage validated under its existing own dispatcher. Kuru-owned main/candidate/migration refs use existing version-aware schema/receipt and structural readers; no graph decoder is added. Native fsck provides chunk/ref/history validation; actual SQL reads and existing validators cover retained working sets, so a dirty candidate is preserved without falsely requiring all history to be current or clean. Main must satisfy the existing Kuru activation/migration contract. Arbitrary extra native refs are retained, not truncated or converted into Kuru candidates.

Reject filesystem copying of a changing live directory and separately captured row/branch snapshots: neither establishes one native dataset cut. Reject stopping writers or acquiring the maintenance permit for backup: the native operation already supplies the cut and the service supplies ownership.

### One bounded manifest, immutable image and truthful native verify

`backup.rs` owns a versioned manifest, physical directory/file inventory, digests, completed root, captured main schema, engine provenance, canonical source storage identity, historical scope, SQL origin and actual native ref observations. Stream file hashing and metadata inspection under retained checked handles. Bounds constrain metadata/path/diagnostic allocation and framing, not total retained history bytes or reachable commits. Ref inventories are streamed and bounded by the manifest's actual encoded capacity rather than a new semantic candidate/history count policy.

Native NBS header reading is limited to the pinned v5 prefix/root, with exact format checks; Dolt owns every graph/table codec. A public `verify_backup` is asynchronous because it validates a private native restore plus `fsck --quiet` without repair flags, schema/ref/working-set reads and owned close. It preserves the original backup bytes and reports only bounded safe root/schema/ref-count metadata. Byte/inventory validation is an internal prerequisite, never the full restorability claim.

Accept ordinary checked destination parents with `Privacy::Inherited` while creating/staging/publishing owner-private children. Reject links, target overwrite, substituted names, duplicate/malformed inventory and metadata/root disagreement. Reject exact-current engine/schema equality as a compatibility rule: engine version is provenance; the bundled reader must actually accept the native format and the immutable registry must validate the captured schema. No promise is made for an image the native reader or released registry rejects.

### Native completion and retained all-exit cleanup

Keep the existing four-hour backup/native operation budget and package-owned startup/close/termination allowances where they fit. A budget bounds the caller, not native completion. Both native output pipes drain concurrently to EOF with bounded retained diagnostics/byte facts; excess progress is discarded from retention while still drained, never a reason to stop reading. Never expose record bodies, auth secrets or native path dumps in success output.

Use existing checked platform launches and memory-owned operation cleanup to retain the exact native child, private home/stage and relevant lifecycle/maintenance objects across dropped callers and generic setup/read/wait errors. Cancellation requests shutdown of that same retained operation; no replay or PID/port takeover follows. When bounded cleanup refuses, the concrete cleanup owner continues observation/reap and holds exclusion until actually settled. The existing memory supervisor owns SQL validation servers and keeps lifecycle authority through EOF/reap; any focused standalone image-command adapter must use platform spawn isolation and retain the same ownership on every exit. No broad engine supervisor rewrite or generic command framework is planned.

The service observes backup connection EOF while awaiting preparation, withdraws publication authority and cancels/settles the dedicated SQL/native work. Publication is a synchronous checked absent-directory move after validation and close. A lost reply after that move is an uncertain request outcome; explicit verification of the destination proves image validity, without proving an earlier unobserved request identity or automatically resending backup. No durable backup receipt table is needed.

### Restore behind the one existing maintenance permit

The public facade obtains `service::MaintenancePermit` before any restore intent, then calls the private owning store restore worker. Do not nest a second native exclusive lock in low-level restore. The permit retains the exact canonical native barrier, start/owner gates and checked directory identities through stage construction, migration, native cleanup and publication. Existing live claims or escaped local cleanup refuse before target effects. The CLI delegates restore maintenance to this package permit, avoiding its redundant project lock; other standalone writer policy remains intact.

Require absent managed target and explicit root-remap opt-in. Restore native bytes into a new private sibling stage; capture and validate the original root/ref inventory before migration. Native validation may use a disposable private copy and must not mutate the input image. Apply missing migrations in the unpublished restore stage through the existing isolated build/publication runner, preserving every original ref/receipt and retained historical candidate rather than stamping all refs current. A checked restore provenance/ready marker binds original backup digest/root and source scope/identity to the final migrated target; the original backup remains the immutable original dataset cut.

Ordinary writable main validation requires a clean base so a later owned commit cannot silently absorb unrelated dirty data. Usage additionally binds clean content to its validated state hash and validates owned ledger identities. Preserve those checks unchanged. After original-image validation, prepare dirty main and usage in the private restore target at any supported schema: capture exact original head, staged and working roots; native staged-only commit preserves a distinct staged snapshot, then native `-A` commit preserves a distinct working snapshot. Each resulting committed root must equal its captured source root, and the final preparation root must equal original WORKING before migration starts. Original heads remain reachable history; restore provenance retains original coordinates and the distinguishable snapshot commit identities. Current-schema dirty main/usage therefore activates clean through appended native commits, rather than claiming its active head/staged/working coordinates remain unchanged. Other candidate, tag and remote refs and their working sets remain untouched. Released migrations consume the clean actual-working-values base, so source-preserving topology conversion reads those latest values; usage uses its existing independent registry. This preparation is neither original-image validation nor an overwrite of the source cut. Reject a permanent restore-origin exemption from clean validation: initial provenance cannot authorize later unrelated anomalies. No generic JSON merge or validation exception is introduced.

Stop/reap all owned workers, obtain the existing stopped-stage lifecycle seal, revalidate source backup/stage/target identities, and publish with checked absent move. Recover only a validated ready restore stage under retained checked startup/lifecycle ownership; an interrupted/unready/uncertain stage remains preserved and cannot be synthesized from SQL state. Use the existing interrupted-stage discipline, not a new restoration journal or automatic source retry.

### Historical namespace is data; canonical target identity remains authority

Extend current activation/identity records with checked optional restore provenance. Ordinary format-1 stores retain their current interpretation. A restored identity has fresh instance/credentials and a separately retained immutable SQL-origin tuple; server authentication checks copied `kuru_instance` against that origin, while service handshakes, expected-existing reopen and native lease paths check the fresh canonical target. Never rewrite historical instance rows/receipts merely to make target authentication pass.

Expose a narrow memory-owned checked `history_scope` getter/attachment metadata. Runtime/CLI persisted namespace consumers use it for session state, topology, notes/private history, preferences and undo; constructor/workspace trust, authenticated project equality, native maintenance and claims retain the canonical target scope. Owner session-mutation key checks use the verified historical prefix while client/claim identity remains the target's fresh proof. Backup-of-restore records immediate source storage authority separately from original SQL/history origin. No string alias grants source capabilities or copies old claim proof into a new generation.

### CLI and source ownership

Add typed provider-free Memory subcommands with explicit backup/input paths and root-remap flag, fixed safe completion output and actionable absent/busy/uncertain errors. Backup requires existing memory and never imports/creates a project; verify requires no project writer/service start; restore requires absent target and package maintenance. Use current configuration/trust preflight for the selected memory data path without constructing inference/tool authority.

Owned sources are memory backup/store/server/facade/service/RPC and fixtures, Memory CLI enums/dispatch plus narrow history-scope runtime consumers, and owning docs. Product D2 owns updater/install functions and later startup image-selection/config seams in separate history; Luna O3 owns its separate warm attachment/provider work. Coordinate stable commits for shared files. Advance one private protocol minor and regenerate its exact golden through the documented owning mechanism; no parallel pin claim.

## Risks / Trade-offs

- [Native procedure returns success without a complete image] → Derive completed root, native restore/fsck and actual ref/SQL validation before publication; pinned fixtures exercise corruption with recomputed physical hashes.
- [Native fsck skips working sets] → Use actual per-ref working-set/schema observations under existing validators; preserve dirty candidates and refuse malformed authority rather than report them clean.
- [Long validation cost and large progress] → Stream inventory and drain output with bounded retention; budgets remain operational, no graph/history truncation or invented performance gate.
- [Migration mutates a restored copy] → Record captured root before migration, preserve input image and all source/history refs, validate staging before ready/publication.
- [Remap conflates history and authority] → Separate fresh target identity/canonical locks from checked historical scope and immutable SQL origin, with real resumed-session/claim refusal tests.
- [Cancelled caller or owner loss] → Retain concrete native/SQL work and named stage, await/reap before release or preserve uncertainty; test dropped caller and maintenance exclusion at actual ownership boundaries.

## Operational surface

The public surface is `kuru memory backup <target>`, `kuru memory verify <backup>` and `kuru memory restore <backup> [--remap-project]`, using the existing explicit memory data-directory configuration for the target. Backup requires an existing project; restore requires an absent target. Verify starts no project owner/provider and creates only disposable private validation state. Success output reports safe image/root/schema/ref-count metadata, never record bodies or connection secrets. Refusals distinguish existing target, unsupported/corrupt image, active/draining maintenance, missing remap authorization and uncertain accepted work; private retained-stage paths may be named only as recovery diagnostics.

There is no new bind address, public listener, container service, credential/environment requirement or connection-limit policy. The existing private per-project IPC and authenticated loopback SQL owner remain the runtime topology on native runners. Native commands use the target's already verified bundled Dolt 2.3.5/archive/licenses and private home, with no download or host fallback. Existing supported architectures and native CI own acceptance; host/Windows-target compilation alone does not establish support. Backup's dedicated exchange/SQL/validation connections release after actual cleanup, and no idle service retention follows. Existing operation/startup/close budgets and unchanged service-frame bounds remain explicit rather than synthetic progress/completion timers.

## Integration contract

The pinned external contract is `DOLT_BACKUP('sync-url', file_url)`, native `dolt backup restore`, and `dolt fsck --quiet` without repair flags. Kuru supplies only retained private stage paths and known native arguments; it neither mounts an arbitrary graph codec nor opens caller-provided SQL. The completed native destination root, immutable file inventory, actual native ref/working-set reads and existing released schema validators reconcile image provenance to the bundled reader. Engine version remains capture provenance, and supported schema comes from validated `kuru_schema`/migration receipts rather than the running binary's manifest expectations. Working-set checks remain explicit because native fsck's commit-ref traversal skips them.

The private additive backup request/reply uses the existing authenticated canonical project, store instance, generation and bounded framing; the coordinated minor/golden update prevents an older owner accepting an unknown operation. Restore supplies fresh external identity/credentials while binding the copied SQL-origin tuple and retained history scope through checked activation metadata. Session claims and native locks continue to use the canonical target, not the historical namespace or source receipt ID. Fixtures use actual bundled offline native Dolt plus two claimed session writers, private restored targets and fault/cancellation barriers; provider-only mocks cannot establish native backup validity or cleanup.
