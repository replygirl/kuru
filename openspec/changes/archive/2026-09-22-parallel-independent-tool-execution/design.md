## Context

The speaking loop currently awaits each provider call before admitting the next. `ToolHost::execute_dispatch` combines permission, checked target and nested-instruction decisions with the effect, while search admits per-file candidates. `PermissionOutcome::OnceAuthorized` is deliberately bound to immediate dispatch and has no transferable token. Native filesystem reads currently use synchronous checked operations; `web_fetch` already owns a separate bounded request and validates each actual connection and redirect. The runtime has an existing `max_parallel` bound, settled tool observations, and a TUI activity collection, but provider result continuation is ordered.

## Goals / Non-Goals

**Goals:** Build the smallest ordered admission and bounded execution seam that overlaps the complete set of proven independent native reads while retaining the current ToolHost's authority rules. Keep provider continuation order and existing compatible event wire shape.

**Non-Goals:** A general dependency graph, model-supplied independence declarations, parallel mutation, shell or MCP effect inference, a transferable Once grant, new network policy, or a new runtime process/setting.

## Decisions

1. **A contiguous wave is assembled only from checked, already-authorized native reads.** The runtime walks calls in provider order, consumes budget once per proposed call, and asks the connector to classify and prepare it. Preparation binds immutable arguments, checked target or bounded search candidate set, permission result, root and instruction authority, plus the real session/turn/actor/invocation identity and exact provider call ID already admitted for that call. Checked execution keeps that `ToolInvocationContext`; it never substitutes an unattributed actor origin. The runtime flushes the current wave before any serial call and before starting the next wave. A model argument is never an effect classification. This is narrower than a general scheduler or speculative execution, which would complicate permission and result dependencies without satisfying another Phase 2 row.
2. **Foreground and authority-changing calls remain immediate serial boundaries.** A fresh approval, especially `OnceAuthorized`, executes through the existing request-bound path before another call is admitted. Candidate-level search approval follows the same rule. A proposed nested-instruction publication is serialized and causes later calls in that completion to return replan receipts rather than run under the old prompt. Rechecking only after a parallel dispatch would let stale instructions leak into an already-started effect, so such calls do not enter a wave.
3. **Checked execution revalidates, it does not re-approve.** Before each prepared read exposes data or sends a fetch, ToolHost rechecks the retained workspace, effective grant state and instruction generation against preparation. Files and search candidates retain their admitted native handles and checked parent/name identities; execution reads those handles and refuses publication when a name is rebound. Directory listing retains and revalidates the admitted directory identity around enumeration. A mismatch refuses or requests replan; it never silently changes the reviewed candidate set, consumes a second Once grant or retries an uncertain operation. Search keeps its existing bounded omission accounting and each candidate's exact deny before any instruction review. `web_fetch` retains connection-time DNS/address and redirect checks inside each independently owned request. A permanent web-fetch exclusion would not follow the roadmap or this existing isolated GET contract.
4. **File reads run on bounded blocking workers; fetches remain asynchronous.** Synchronous checked file/list/search work must leave the executor free to poll another call, and the number of in-flight workers is capped by the existing parallel limit and remaining tool budget. The wave owns every task until completion or cancellation drain; it never detaches workers that can later publish a result. Avoid merely joining blocking futures on one executor task, which would produce no actual overlap.
   Retained native target handles also use one small ToolHost-wide RAII budget charged for every ancestor and file handle across all prepared calls. A call that cannot reserve its complete capture set drops its partial captures and follows the ordinary serial path, preserving the existing search limits and complete serial result rather than truncating candidates.
5. **Settlement order and continuation order are separate.** The runtime emits start and settled observations as calls actually enter and finish. It stores each bounded result by original call position and appends the protocol continuation only after the wave drains. The TUI's activity set keeps every still-running call; same-name calls remain distinct internally by provider call ID while the compatible event wire stays three-key. This is preferable to sorting progress, which would falsely show a completed call as active.

## Risks / Trade-offs

- **Authority changes between ordered preparation and execution** → retain checked permission facts and instruction generation, revalidate at each effect, and refuse/replan on mismatch. Do not broaden a candidate set at execution.
- **Fresh approval cannot be safely held across later admission** → that entire call is a serial barrier, including search when one candidate needs the foreground; ordinary previously granted calls still overlap.
- **Synchronous file work could block the executor or outlive cancellation** → use bounded owned blocking work and wait for its terminal cleanup before turn return; cover cancel during the worker's actual effect window.
- **Exact candidate identity could retain more native handles than the process limit** → reserve the whole capture from one ToolHost-wide handle budget, release permits with the captured capabilities, and use ordinary serial execution when the capture does not fit.
- **Results may finish out of provider order** → settle progress immediately but build provider tool results from indexed slots only after every wave call has reached a terminal outcome.

## Operational surface

The existing local CLI/TUI and provider transport remain the only execution surfaces. No bind address, container boundary, required secret, binary version or architecture changes. `max_parallel` remains the bound for work admitted by one runtime, and native supported-platform checks exercise the same checked filesystem and HTTP paths. The TUI shows concurrent activity from projected events; no scheduler controls are added to the user interface.
