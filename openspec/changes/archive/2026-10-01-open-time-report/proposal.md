# Proposal

## Why

Phase 1 of the startup regression needs open times for the release binary a user runs on ubuntu-latest, measured in CI; no record has any, and nothing times the owner's open from inside a release build. Phase 1 added a report-only measurement, from outside the binary, inside `ci.yml`, as the first form of the open-time budget check. Phase 2, this revision, turns that report into the gate: the store-creation work (unit 1, `d717b4fd`) is on main, so main's engine-start counts per case and the new-project and cold-existing median open times are now a contract worth protecting, not just a number worth watching. macOS numbers remain one-off local runs of the same harness, not a CI job; Windows open time is still not measured or documented here.

This is also P0 of the store creation work (`tmp/roadmap/store-creation-design-machine-cache-2026-09-29.md` section 11): the acceptance instrument that must exist, with a `new-project` case and a warm-engine baseline, before the template-cache PRs land, so their before/after engine-start counts have something to compare against. Section 12 (M3) names this job and a local macOS run as the measurement points for every PR in that split.

## What Changes

- `packages/kuru-delivery/src/open_time.rs` and `src/open_time/`: an `open-time` subcommand of the maintainer `kuru-delivery` tool, behind the unshipped `tooling` feature. It drives a release `kuru` in isolated scratch roots through four cases, in order (first launch ever, first open of an existing project with no live owner, warm reopen inside the owner's idle window, and — appended after those three and their own retirement wait — a second, different project created in the same scratch root, so its engine cache is already warm and only the project is new), timestamps its stderr progress lines, and observes processes (sysinfo) and directory listings under the scratch root, never opening a file and never entering the install stage, store staging, interrupted or template-cache build/stage directories the product renames. It cuts each open at ordered milestones into stages that partition it, reports nesting spans as totals with their parts, and states the recorded sampling bracket as the error bound. Before and after each run it takes a census of what can accumulate (this user's Kuru and Dolt processes, open handles and listening ports of the scratch root's processes, staging and interrupted directories) and records the owner's retirement time. A control mode lists no files, and a ramp mode runs consecutive opens without retirement waits. In the `new-project` case the stores already in the data directory are named `<prior-project>`, so the new project's store is seen appearing. It writes one `kuru.open-time.v3` JSON record per run (v3: the fourth case, the ready signal and the parsed markers, and the final milestone named `ready` for either signal) and a summary table. Phase 2 adds a gate mode (`src/open_time/gate.rs`, a pure function over the records' projection), read from six environment variables that must be set all together or not at all: `KURU_OPEN_TIME_EXPECT_FIRST_LAUNCH_STARTS`, `KURU_OPEN_TIME_EXPECT_COLD_EXISTING_STARTS` and `KURU_OPEN_TIME_EXPECT_NEW_PROJECT_STARTS` (exact `Counts.engine_starts` of every run of the case), `KURU_OPEN_TIME_EXPECT_WARM_REOPEN_STARTS` (keyed on `Record.path`'s `OwnerPath`, for example `attached=0,spawned-owner=1`, so an `attached` and a `spawned-owner` warm reopen carry different expectations and a path not listed fails), and `KURU_OPEN_TIME_BUDGET_NEW_PROJECT_MS` and `KURU_OPEN_TIME_BUDGET_COLD_EXISTING_MS` (budgets for the case's median open-to-ready time over the main series). The structural checks run first, over every case: the case has runs, every run opened (a failed open with coincidentally matching counts would otherwise pass and shrink a median), and every run's engine starts match. Only once all of those hold are the new-project and then the cold-existing medians checked. Any violation is written to the summary (which case, observed vs. expected or budget, the offending iterations) and the command exits non-zero after every record has been written. Runner noise can move a median but not a count, so a first series that holds every structural check but misses a median budget is followed, in the same command, by one more full main series (same n and cases, fresh scratch root, records in `<output>/retry/records.jsonl`); both series are reported, and the gate fails only if the second series fails a check too. A structural violation in either series fails at once, there is never a third series, and a persistent miss is fixed by re-deriving the budgets. The gate refuses the control and ramp modes (budgets derive from the main series), and a partial set of gate variables is an error before anything is measured. Without the gate variables set the command stays exactly as report-only as before.
- The harness reads the end of an open from either of two signals: the legacy `Memory: ready.`/`Memory: waiting for project ownership…` stderr lines, or, when a run's binary supports it, the `kuru-open-marker v1 <event> <monotonic_ns>` stderr lines (`open-start`, `waiting-ownership`, `ready`) that a separate, not-yet-merged change emits when `KURU_OPEN_MARKERS=1` is set. The harness sets that variable on every run it launches so both old and new binaries measure; a marker takes the place of its legacy line, the interval still ends at the harness's read time of the line, and the record names which signal ended the open (`stages.ready_signal`). Markers and the agreed plain open sentences are progress: kept in the record, never a failed run's error line.
- `packages/kuru-delivery/tests/fixtures/delivery.rs`, `tests/open_time.rs`: a live-subprocess fixture that stands in for `kuru` and drives the harness end to end; extended to emit markers only when `KURU_OPEN_MARKERS=1` reaches it, both signals by default, legacy lines only (a binary from before the marker change), markers and the plain sentence only (a binary from after it), and neither (a failed open), and to name each project's store by the hash of its directory, so the harness's reading of each signal and the new-project case are tested against a live process. Phase 2 adds tests of the `kuru-delivery open-time` command itself against that fixture: a passing gate exits zero, a violated one exits non-zero after writing every record and the summary, no gate variable keeps it report only, and a partial gate or a gated control series is refused before measuring. `src/open_time/testdata/gate-36949202478.jsonl` and `gate-36952763676.jsonl` are the main-series records of the two post-fix derivation runs, trimmed to the fields the gate reads; the gate's unit tests run on them (both pass) and on single-field mutations of them (one failing set per check), and recompute both budgets from them and compare `ci.yml`. `tests/release_workflow.rs` pins the gate job's shape and `ci-gate`'s needs.
- `packages/kuru-delivery/mise.toml`: `measure:open-time` task.
- `Cargo.toml`, `packages/kuru-delivery/Cargo.toml`, `Cargo.lock`: `sysinfo =0.39.6` (feature `system` only), optional under `tooling`. The shipping `kuru` dependency tree is unchanged on every target.
- `.github/workflows/native-tests.yml`: the ubuntu-latest install job publishes its installed release binary as an artifact. Phase 2 removes that upload step's `continue-on-error`: a gate input must be a hard step, so an upload failure now fails the ubuntu install job itself. Linux-only, unchanged; the other install jobs (macOS, Windows, Windows on Arm) still do not upload.
- `.github/workflows/ci.yml`: the `open-time` job is renamed (for example "Open-time gate (ubuntu-latest)"), loses its job-level `continue-on-error` and its `if: ${{ !cancelled() }}` condition, keeps `needs: native-tests`, and joins `ci-gate.needs` (so `ci-gate`'s `jq` step, which already requires every needs entry's `result` to be `success`, now requires this one too). It runs the main series only (`n=10`); the control, coarse and ramp steps are removed from CI (the mise task keeps those modes for local use). It passes the gate's environment variables in the job's own `env` (engine starts first-launch 3, cold-existing 1, warm-reopen `attached=0,spawned-owner=1`, new-project 2), with the two budget constants each commented with the two post-fix derivation runs it was computed from, 36949202478 (head 306bf7fd) and 36952763676 (head 7dea51fb), both measuring main at 0e562595, and the rule (highest post-fix median of the case across those runs, plus three times the largest within-run spread of that case, rounded up to a whole ms): new-project 731.9 + 3 × 52.6 = 889.7, so 890 ms; cold-existing 399.3 + 3 × 61.7 = 584.4, so 585 ms. The records upload keeps its step-level `if: ${{ !cancelled() }}` so a failed gate still ships its records for diagnosis. No `workflow_dispatch`, no new workflow file, pins unchanged (actions stay pinned by commit SHA as the file already does).
- `docs/development.md`: what the job measures, the four cases and their expected engine-start counts, both readiness signals and the `KURU_OPEN_MARKERS` switch, the stages and their error bounds, the census and modes, which build profile the packaged embedded-runtime test runs in coverage partitions, how to read it, and — replacing the phase 1 "never compared with a budget" language — that the job now gates on exact counts and on the new-project and cold-existing medians, the budget rule and how to re-derive a budget after a deliberate startup change, that the control/coarse/ramp modes remain local-only (`measure:open-time` with their env vars), and that macOS numbers are local one-off runs while Windows open time is not measured.

## Impact

Phase 2 makes `open-time` a required check: `ci-gate` now waits on it, and its own `needs: native-tests` plus a main-series run of `n=10` (about 70-90 s per iteration with two 30 s retirement waits) adds roughly 15-20 minutes to `ci-gate`'s critical path after `native-tests` completes. The install job's release-binary upload step is no longer `continue-on-error`, so an upload failure now fails that gating install job rather than being swallowed. No product code, no product dependency, no secrets, no permissions and no action pins change; no new required-check name beyond the renamed job, and no new workflow file. The job builds only `kuru-delivery`, which does not depend on `kuru-memory`, so it needs no engine bundle input. This change adds no marker emission itself: reading `kuru-open-marker` lines is additive and the harness keeps working, on the legacy signal only, against a binary from before the marker-emitting change merges. The gate's own CI run on this change's pull request is the proof that the counts and both budgets hold on main's current startup path.
