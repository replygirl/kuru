## Context

`apps/kuru-tui/src/cli.rs` defines the Clap `Cli` and subcommand tree; the command variants are not target-gated. The delivery packager, Rust updater, Unix bootstrap and PowerShell bootstrap all validate the current three-member executable archive exactly. Adding shell files to that archive would make published older readers reject a new release. The Phase 2 plan says the files ship in release archives, without requiring that they occupy the executable archive, and separates shell-asset delivery from the Homebrew tap/formula.

## Goals / Non-Goals

**Goals:** derive current shell/man content from the authoritative CLI, ship it with exact release identity, preserve older executable-update compatibility, and make new managed installations and updates able to install the support files without changing shell profiles.

**Non-Goals:** Homebrew formula/tap publication, P25 rollback or update notices, a new shell configuration service, changed runtime authority, or a general transaction framework for unrelated files.

## Decisions

### Generate from the app's Clap command before authority activation

`apps/kuru-tui` owns pure `kuru completions <bash|zsh|fish|powershell>` and `kuru man` output driven by `Cli::command()`. Dispatch these before project path resolution, configuration/trust preflight, memory ownership, provider creation or tool startup. The package-owned mise task uses the already-built release binary to write five bounded outputs; `kuru-delivery` consumes them as read-only, checked build inputs and never compiles the app or memory. Initially select exact workspace pins `clap_complete =4.6.9` and `clap_mangen =0.2.33` alongside existing `clap =4.6.6`, then verify resolution and update Cargo.lock in implementation. Both selected generators declare Clap 4 compatibility; use their ordinary stable generation APIs, not dynamic completion or build-script side effects. One `kuru.1` must contain the actual current command/options tree, including nested command help, rather than only a top-level synopsis.

An alternative hand-written shell/man template would duplicate the parser and drift as P11 and later commands land. A delivery-owned generator would invert package ownership and couple packaging to app internals.

### Ship fixed content in the two native archive envelopes

The content inventory of each target-specific sidecar is exactly `completions/kuru.bash`, `completions/_kuru`, `completions/kuru.fish`, `completions/kuru.ps1`, and `man/kuru.1`, all regular files with bounded sizes and no absolute, traversal, link or duplicate entries. Pair each core archive `kuru-<version>-<target>.<format>` with `kuru-<version>-<target>-shell-support.<format>` in `SHA256SUMS`: tar.gz for each Unix target and ZIP for Windows. This lets existing Unix tar/gzip and PowerShell ZIP facilities validate their native format without a new prerequisite. Generate the five files from that exact target's final binary, then verify the sidecar checksum, inventory and file content against its paired build. Different targets may legitimately yield different CLI content; there is no common-content comparison. Keep each existing platform executable archive's three-member layout and name unchanged.

An alternative expanded executable archive would strand already-published strict readers, including v0.4.1/v0.4.2. A single physical sidecar format would add a parser or tool dependency to one bootstrap, and a common cross-target sidecar would constrain future target-specific CLI commands. None is needed to satisfy the plan's “release archives” wording.

### Stage support before replacing the executable

New bootstrap/update flows select one explicit release version and target, fetch its paired support envelope and core archive, verify both against the checksum manifest, and validate all decoded support members before touching the installed binary. A checked, versioned support directory under the selected installation root (for example `<install-dir>/share/kuru/<version>/<target>/`) receives the exact files. Publish that directory before invoking the existing executable replacement path. A support verification/publication failure leaves the old executable untouched. If executable publication then fails, remove only an exactly owned new support directory when safe or retain it as an unreferenced versioned directory with a truthful diagnostic; never claim full installation. A restart may reuse it only after exact version/target/content validation. Retain older version directories for a compatible executable rollback; do not treat support bytes as memory or a credential store.

The executable's existing receipt remains the authority for replacement and recovery; no second selector, symlink, junction, digest gate or shell-support transaction is introduced. After confirmed executable publication, the current installer uses existing checked regular-file publication to update `<install-root>/share/man/man1/kuru.1` from the exact verified versioned snapshot. A successful current installer/update reports success only after matching versioned support bytes, executable and stable man file have been confirmed. A failed or uncertain executable publication leaves the stable man file alone and does not claim completed support for that release; retry uses the existing executable receipt and revalidates any retained versioned directory before reuse. A stable-man publication failure after binary success is reported as partial, with a concrete current-installer retry or pure generation repair path. Never delete a directory or file without exact owned identity and content checks, and never claim executable-plus-support atomicity.

Absence of a support checksum entry alone never means legacy. The bounded README member in every new core archive carries one exact `<!-- kuru-shell-support-format: 1 -->` line near its start; the current packager and candidate/published verifiers require it. A new reader inspects this line only after verifying the core checksum and decoded three-member inventory. The parser accepts an unmarked historical README as pre-support, requires that core target's paired support envelope and checksum entry for marker version 1, and rejects malformed, duplicate or unsupported marker forms. A marked new core with a missing sidecar fails before executable mutation; an accidentally unmarked candidate cannot pass the new release assembly or verifier. Existing v0.4.1/v0.4.2 Rust readers decode README to a sink, the Unix bootstrap checks only names/types, and the PowerShell ZIP reader checks names/modes but not README text, so this line does not change their three-member compatibility contract. Already-published older updaters can still install the unchanged core archive. To repair missing managed support after such an update, the user can run the current verified bootstrap again for that exact version and install root; it validates and installs the sidecar. Alternatively, the newly installed binary's pure `kuru completions` and `kuru man` commands can write explicit user-managed files, without claiming that the older updater installed the managed sidecar. No app-start download or profile edit occurs.

### Keep activation explicit and destination-owned

The direct bootstraps place support under their explicit install directory, not arbitrary `$HOME` profile or shell configuration paths. The stable direct-install completion activation interface is the installed executable path, not a versioned file path. Documentation gives explicit stock-shell snippets: Bash/Zsh source the output of `<install-root>/kuru completions bash|zsh` using process substitution, Fish pipes `<install-root>/kuru completions fish` to `source`, and PowerShell evaluates the local installed `<install-root>/kuru.exe completions powershell` output. These commands are pure generation from the current executable, not a network fetch. The persistent profile snippet contains the stable explicit executable path, never a versioned support path; after a settled update, a new shell session or explicit reload obtains the new command tree. An already-running shell keeps its earlier loaded completions until reloaded. On Unix the stable regular file `<install-root>/share/man/man1/kuru.1` supports one-time `MANPATH=<install-root>/share/man:$MANPATH` setup and ordinary `man kuru`; `kuru man` remains a pure direct view/repair route. There is no Windows man-viewer prerequisite. During an unresolved replacement no continuously synchronized activation is promised; the user runs the existing update recovery before relying on the installed result. No installer edits a user's profile or starts downloads at app launch. The immutable versioned files at `<install-root>/share/kuru/<version>/<target>/completions/...` and `man/kuru.1` remain verified, installable pinned snapshots for offline and package use, not the recommended persistent direct-install profile path. P24b's eventual Homebrew formula can place the same verified files in Homebrew's conventional shell/man directories. The release workflow, candidate assembler, checksum manifest, staged Windows verifier, published-download verifier, install/update fixtures and docs update their exact asset counts together; their executable archive member validation remains strict.

## Risks / Trade-offs

- [A later CLI change yields stale generated output] → generate and verify each sidecar against its own final native release binary before candidate publication.
- [A support directory is published but executable replacement fails or crashes] → keep it versioned and unreferenced, perform only identity-checked cleanup, and report the executable outcome according to its existing receipt. Do not claim cross-file atomicity.
- [An old updater upgrades only the core binary] → retain exact core archive compatibility and document a concrete pure local regeneration command from the new binary.
- [An explicit install directory does not lie on shell or man search paths] → document generation from the fixed installed executable path and explicit shell reload; never silently modify user profiles.

## Operational surface

The generation route runs inside the ordinary target-specific `kuru` executable on each existing native release runner; it opens no listener, uses no container, credentials, account, provider, network connection or memory service, and imposes no connection limit. The release jobs already build the supported macOS, Linux and Windows targets with their embedded engine; the app-owned task runs that exact selected executable after build. Direct installers use only the explicit version and install root already selected by their invocations. The PowerShell path continues to use stock Windows PowerShell/.NET and the existing ZIP reader; Unix continues to use tar/gzip. No new service lifecycle or automatic startup check is introduced.

## Integration contract

`apps/kuru-tui` owns the Clap command factory and five generated source bytes for its selected target. `packages/kuru-delivery` owns the five exact target-paired envelope names, normalized archive metadata, checksum entries, checked version/target directories and verified installation/published-read paths. The Release workflow hands only bounded generated files and paired platform archives between native build jobs and candidate assembly; it verifies each sidecar against its target binary rather than imposing cross-target byte equality. Each support envelope's path inventory is fixed by the `shell-support` delta spec. Existing core archive names, three-member format, selected release version and executable replacement receipts keep their current meanings. There is no mount, HTTP route, SDK account, database ID or schema conversion in this change; old client compatibility is at the immutable archive-name/member contract, and Homebrew formula/tap ownership remains outside this change.
