# Design

## Context

### What the CI logs show

The three catalogued windows-latest failures have two different mechanisms. The job logs establish this directly.

- **M1, teardown swallowed** (item 6; PR #115, job 108544879759). The assertion `!stage_path.exists()` failed ("cancellation drops the private stage before releasing the cache lock"), so the task *was* cancelled. On main, cancellation drops `StagedActivation` in field order: source handle, probe, `PrivateTemp`, `CacheLock`. `PrivateTemp` drops its `tempfile::TempDir`, whose `Drop` calls `remove_dir_all` and discards any error. A transient Windows handle inside the stage (antivirus or the indexer on the just-extracted `dolt.exe`, or the image section of the just-run probe) makes that removal fail. The lock is then released with the stage still present, and nothing records it.
- **M2, first result after the window** (item 1: PR #110, job 108484586358; new occurrence: PR #124, job 108878373677). Job 108878373677 panicked at `native_tests.rs:947:24` on `task.await.unwrap_err()`, which received `Ok(Err(..))`. The task completed rather than being cancelled. Its error chain is `verified Dolt activation failed; preserved private stage` → `activate verified Dolt runtime` → `memory directory reconciliation proved the held source remains and the destination is absent` → `Rejected … Access is denied. (os error 5)`, with **no** `runtime activation recovery stopped` context. In the main Windows loop, a proven no-move with os error 5 skips that context only when `first_error` is still `None`, which means the first attempt, and `now >= deadline`. So the first `activate_once` returned only after `ACTIVATION_RETRY_LIMIT` had elapsed. `observer(true)` (which aborted) was followed by `retain` and a return with no await, so the abort never landed. Item 1 has the same shape. Its assertions that elapsed ≥ the window, that `checked_denials >= 1`, `Rejected` and os error 5 all passed, and then `contains("runtime activation recovery stopped")` failed. The logs have no per-test timing, so the ≥2 s first attempt is inferred: the error chain allows no other path. It was not measured.

### Other ordering defects found by reading

- Extraction error: `let (staging, lock, extraction) = …; extraction?;` drops the pattern's bindings in reverse order, so `lock` is released before `staging` is removed. A local probe (`droporder.rs`, compiled with the pinned toolchain) printed `drop lock` then `drop staging`.
- Published path (review S5): `finish_published` released the lock, and the caller wrote the `.leftovers` receipt only afterwards.
- `CheckedColdProbe::probe` and the probe-preparation error path dropped the stage through `TempDir::drop`, so a failed removal was discarded there too.

### Removal semantics

`PrivateTemp::close` removes the stage through `kuru_platform`'s checked `Directory::remove_tree` inside the existing bounded recovery (`close_windows_private_stage`, `CLEANUP_RETRY_LIMIT` = 2 s) on Windows, and through `TempDir::close`, which reports its error, on Unix. The Windows checked removal deliberately uses the legacy `FileDispositionInfo` and never POSIX unlink (`packages/kuru-platform/src/fs/windows.rs`). A share-delete handle on a descendant therefore leaves that name delete-pending until the handle closes, and its parent cannot be removed until then. `std::fs::remove_dir_all`, which `TempDir::drop` uses, removes the name immediately with POSIX semantics.

## Goals / Non-Goals

**Goals:**
- One owner (`StageLease`) orders stage resolution before lock release on every path. Stage resolution is removal, reported and receipted retention, or named evidence.
- A Windows activation cancelled while recovery is waiting to retry is cancelled with lease teardown, and recovery that ends on a recoverable denial, even a late first one, is always reported as stopped recovery with a named, preserved stage.
- Deterministic regression tests: Unix variants run locally; `cfg(windows)` variants run in the windows-latest and windows-11-arm partitions. Their observation of the report-before-release order does not depend on test scheduling or on which thread resolves the lease (decision 8).

**Non-Goals:**
- Changing any deadline, spacing, retry limit or recoverable-error set, or adding a retry loop or sleep.
- Changing `CacheLock` release-by-close. The #124 audit lists it as a follow-on for the shared explicit-release guard.
- Changing the Unix removal mechanism, which stays `TempDir::close`, or the sweep.

## Decisions

1. **The lease records retention; callers do not.** `StageLease { staging, lock, asset }` derives the version directory from the stage container's parent, so the receipt's `relative_to` check holds both in production and in the fixtures under `cache`. `close_published` and `discard_after` share one `release(published)` path. That path runs `close_or_keep` and, on failure, adds context, runs `record_retained_stage` (the receipt) and `emit_retained_stage_diagnostic`, and only then drops the lock. The caller receives an `Option<StageCleanupReport>` and only maps it to a progress stage. *Rejected:* returning a failure value that carries the lock (the draft's `StageTeardownFailure`). That hands the ordering back to every caller and let the published path release before the receipt.
2. **Unpublished retention is receipted.** A stage left by an error or a cancellation is disposable, and the sweep already collects any receipted `.install-*` stage under the lock. The receipt carries `published: false`, and the diagnostic uses a distinct message with the same admitted fields. *Rejected:* diagnostic only. That leaves an uncollectable stage behind on every Windows handle refusal.
3. **Evidence stays evidence.** `keep` (activation failure: occupied destination, a non-recoverable error, recovery exhausted) is unchanged. The stage is preserved on purpose and the returned error names it. This is the third resolution in the contract, not an exception to it.
4. **`Drop` tears down synchronously within the existing bound.** The frozen cancellation test requires the stage to be gone when the `JoinHandle` resolves, so teardown must run as the future is dropped. Moving it to `spawn_blocking` would race that and is unavailable during runtime shutdown. `block_in_place` panics on a current-thread runtime. The previous `TempDir::drop` was synchronous too. The bound is one `remove_dir_all` on Unix and `CLEANUP_RETRY_LIMIT` plus a receipt write on Windows, and only when a handle refuses removal. That bounded block is the documented trade-off (reviewer point on `StageLease::drop`).
5. **Ruling (review S1, verification 4.2): no added cancellation point; the `yield_now` is dropped.** The draft added `tokio::task::yield_now().await` after every checked no-move so that a caller's cancellation would land before the retry-or-stop decision, including the terminal case where the first result arrives after the window. Review S1 showed that the yield also makes the 4 s `tokio::time::timeout` in `persistent_held_descendant_exhausts_checked_recovery_and_preserves_stage` (native_tests.rs:1068) reachable for the first time. The ruling procedure keeps the yield only if that 4 s can be replaced by a fixture deadline derived from the product's own bounded terms (window + the bound on one attempt + the product's allowances, through the PR #101 helper pattern), and drops it otherwise. It is not expressible, because the product defines no bound for one attempt:
   - The recovery window is bounded: `ACTIVATION_RETRY_LIMIT` = 2 s and `ACTIVATION_RETRY_SPACING` = 20 ms (provision.rs:31, 33), measured on the tokio clock from provision.rs:1017. `CLEANUP_RETRY_LIMIT` = 2 s (files.rs:461) bounds only stage removal retries, not a move.
   - One attempt is `activate_once` → `files::move_directory_checked` → `kuru_platform::fs::Directory::move_new_directory` (fs.rs:858) → `native::publish`. That call is synchronous and carries no `Duration`, timeout or deadline anywhere in `kuru-platform/src/fs.rs` or `fs/`. On `STATUS_PENDING` it waits with `WaitForSingleObject(renamed.as_raw_handle(), INFINITE)` in a loop (`packages/kuru-platform/src/fs/windows.rs:866`, 10 ms back-off at :876). The Uncertain-phase reconciliation that follows is likewise unbounded filesystem reads.
   - The PR #101 helper already classifies this: `test_support.rs:191` ("Steps without a product bound, such as warm cache verification, legacy import preparation and activation reads, rely on this backstop alone."). `fixture_deadline` budgets server starts, closes and queries; nothing in it or in `LOCK_TIMEOUT`/`VERSION_TIMEOUT` bounds a native directory move.

   So the yield would be product code whose only consumer is a test's abort timing, which also exposes a flat 4 s that cannot be replaced by a derived bound. It is removed. Cancellation is honoured at the recovery's existing await point, the retry-spacing `sleep` (provision.rs:1058), taken only while the tokio clock is inside the window. When the first recoverable result arrives after the window, no await point follows the terminal decision: the operation completes with the stopped-recovery error (decision 6), keeps and names the stage, and releases the lock only after that. This is safe for the #124 shape, because a completed evidence retention is not a lease-ordering violation: the lock still outlives the stage's resolution. `cancellation_at_a_late_first_checked_no_move_completes_with_stopped_recovery` asserts exactly that, with the abort still issued in the observer. The frozen cancellation test is made deterministic by its fixture (decision 7), not by product code.
6. **A late first recoverable result reports stopped recovery.** If the first recoverable no-move arrives at or after the deadline, the loop returns `expired_activation_error(error, retries)` ("runtime activation recovery stopped after 0 retries before starting another native move"), which is exactly what happened. This preserves the typed `PublicationError` (still downcastable) and os error 5.
7. **Frozen test fixture handle (flagged for review).** `cancelling_checked_activation_recovery_drops_stage_before_cache_lock` held `_parent`, the `runtime` directory handle returned by `files::read`, until the test ended. Under the checked legacy-disposition removal, that handle keeps `runtime` delete-pending, so `private` cannot be emptied, the 2 s window runs out and the stage is retained. The test would then fail deterministically. The old unchecked POSIX `remove_dir_all` bypassed the handle. That incidental handle is not the scenario under test. The smallest change that keeps the test's intent moves it into the observer closure together with `blocker` and drops both on the first proven no-move. Every assertion is unchanged, and so is the order of the blocker release and the abort. Second fixture change, from the decision 5 ruling: the test's intent is the ordering on cancellation (stage resolved before the cache lock is released), and PR #124 (job 108878373677) showed that a first native move slower than the 2 s window instead completed the operation, so `task.await.unwrap_err()` received `Ok(Err(..))`. The orchestrator's suggested controls (hold the first result until the abort is issued, or abort before releasing the observer) do not reach that fault, because the abort is already issued inside the observer, before control returns to the loop; the missing piece is an await point on the late path. The fixture therefore calls `tokio::time::pause()` immediately before spawning the activation, after the real lock acquisition and version probe whose timeouts a paused clock would auto-advance, and `tokio::time::resume()` right after the cancellation is observed. The product's recovery deadline is on the tokio clock, so a slow synchronous first move can no longer close the window, and the cancellation always reaches the retry-spacing wait. This is the pattern `held_descendant_releases_after_checked_no_move_and_activation_recovers` already uses in the same file (native_tests.rs:983, "isolate only this positive retry from runner wall-clock load"). Stage teardown on drop keeps its own wall-clock bound (`std::time::Instant` and `thread::sleep` in `files.rs` 723-755), which a paused tokio clock does not touch. No assertion line changes.

8. **Retention reports are observed through the product's own tracing event, delivered by one process-global recorder (CI round 1, run 36424722859; review M1).** The three tests that prove a retention is receipted and reported while the lock is held first observed the `kuru.memory` diagnostic with a thread-scoped subscriber (`tracing::subscriber::set_default`). That observation is not deterministic. `tracing-core` 0.1.36 caches each callsite's interest process-wide. While exactly one scoped dispatcher is live, `Dispatchers::rebuilder` returns `JustOne`, and a callsite first reached on another thread takes that thread's default (no subscriber), so it is cached as never enabled (`callsite.rs` `rebuild_callsite_interest` via `Rebuilder::JustOne` → `dispatcher::get_default`). A concurrent test without a subscriber that emits the same "after published engine" diagnostic therefore silences it for the capturing test. macOS coverage partition 1 hit this (`one retention report: []` at tests.rs:1891), and running that test beside `exhausted_stage_cleanup_publishes_the_engine_and_receipts_the_retained_stage` at `--test-threads=2` reproduced it in 10 of 20 runs; the receipt was written in every failing run, so the product ordering was intact.

   The first round-1 fix replaced the capture with a `#[cfg(test)]` seam that `StageLease::release` called after `emit_retained_stage_diagnostic`. That seam proved only that the release path reached the observer while the lock was held; it did not observe the event, and a mutation that silenced `emit_retained_stage_diagnostic` passed every provision test (review M1). The spec requires the diagnostic itself before the lock is released (spec.md, "Retained stage after publication"). The seam is therefore removed, and provision.rs is again identical to the pre-round-1 tree; no test hook remains in product code.

   The observation is now the event itself. `provision/native_tests.rs` defines `RetainedStageRecorder`, a `tracing::Subscriber` installed once per test process with `OnceLock` + `tracing::subscriber::set_global_default`. Its `register_callsite` returns `always` for target `kuru.memory` and `never` otherwise. For each `kuru.memory` event whose message starts with "retained private install stage", it reads the `message`, `stage` and `published` fields and calls, synchronously and outside its registry lock, every observer whose path scope contains the event's `stage`. `observe_retained_stage_reports(scope, lock_path)` registers such an observer, which records the event's full message, `published` and `stage` together with two probes taken at that instant: the `.leftovers/<stage>.json` receipt exists, and a fresh handle's `try_lock` gets `WouldBlock`. Each test asserts one observation with the exact message ("…after published engine" in `published_stage_retention_…`; "…after an unpublished installation" in `failed_extraction_…` and the Windows `cancelled_activation_recovery_receipts_…`), `published == Some(true|false)`, and `receipted && lock_held`.

   Why this is immune to the caching and to test order: a global default is what `dispatcher::get_default` returns on every thread that has no scoped default, and nothing in this test binary sets one, so the `JustOne` rebuild on any thread computes the recorder's interest. One installation gap remains: `Dispatch::new` registers the recorder before `set_global_default` stores it, so a callsite registered on another thread in that gap can cache `never`. tracing-core 0.1.36 links a callsite into its registry before computing its interest (`DefaultCallsite::register`), so `tracing::callsite::rebuild_interest_cache()`, run after installation and again on every observer registration, recomputes it. The only interleaving it does not cover, a registration that read the empty default before the store and wrote its interest after that rebuild, would show as a missing observation and fail the test; it cannot make a test pass. The path-scoped registry means parallel tests with separate directories neither see nor hide each other's events, on whichever thread (a cancelled task's drop, a blocking worker or the caller) resolves the lease.

   Coexistence audit (review M1 condition): the kuru-memory lib test binary has no other `set_default`, `set_global_default`, `with_default`, `tracing_subscriber` or `Subscriber` implementation (`src/`, including `test_support`; kuru-memory has no `tracing-subscriber` dependency), and its dependencies kuru-core, kuru-platform (including the Windows `test-support` feature) and kuru-archive have none. The subscribers in `apps/kuru-tui/src/diagnostics.rs` and `packages/kuru-connectors/src/auth.rs` belong to other test processes, which compile kuru-memory without `cfg(test)` and so without the recorder. The recorder prints nothing and only observes `kuru.memory` events, so other tests' output is unchanged.

   What each check proves: the event observation proves that the product emitted the `kuru.memory` diagnostic with the expected message, `published` and `stage` fields, and that at that instant the receipt existed and the installation lock was held. Two mutations, reverted, are its red evidence: `return` at the top of `emit_retained_stage_diagnostic` fails both Unix tests with `one retention report: []`, and dropping the lock first in `StageLease::release` fails them with `lock_held: false, receipted: true` (verification 5.4). The remaining admitted fields and their bounded truncation are covered by the diagnostics ring tests in `apps/kuru-tui/src/diagnostics.rs`, which use their own copy of the published message rather than the product's emission.

   In the same round, the Windows test counted every entry of `.leftovers`, which also holds the `staging` directory that `files::write` keeps beside the receipt (files.rs:124). The product sweep already skips it (provision.rs:1354). The test now counts `.json` receipts only and also checks the receipt names its stage. No product ordering changed. *Rejected:* a thread-scoped subscriber through `set_default` or `with_default`, with or without a rebuilt interest cache, which keeps the callsite-interest hazard; the release-path seam alone, which does not observe the event; joining the seam to a recorded event, which would probe the lock at the seam rather than at the event.

## Risks / Trade-offs

- [A persistent holder longer than `CLEANUP_RETRY_LIMIT` during a cancelled Windows activation still leaves the stage on disk] → That is now reported and receipted rather than hidden. The frozen test would still fail if a scanner held a handle for more than 2 s, which is the existing bound this change must not raise.
- [The runtime worker blocks for up to 2 s when a cancelled Windows activation meets a refusing handle] → Bounded, rare, and the same class of blocking as the previous synchronous `TempDir::drop`.
- [The M2 mechanism is inferred from the error chain, not timed] → The new Windows regression tests reproduce it deterministically by holding the observer past `ACTIVATION_RETRY_LIMIT`, which is a fixture delay rather than a product one.
- [Review S1: a yield after every checked no-move made the frozen test's 4 s fixture timeout reachable] → Resolved by the decision 5 ruling: the yield is dropped, so every `Pending` point in the Windows loop is again the retry-spacing `sleep` taken only inside the 2 s window, and every terminal branch returns synchronously, as on main. The 4 s in `persistent_held_descendant_exhausts_checked_recovery_and_preserves_stage` is unreachable again for main's reason, and that test is byte-identical to main. The 4 s is still a flat literal, not a derived deadline, and no derived bound can replace it while one native move has no product bound (decision 5). Deriving it is out of scope here, and the value is not raised.
- [A late first result still completes a cancelled activation] → Accepted by the ruling: the operation retains the stage as named evidence and releases the lock afterwards, so the ordering contract holds; only the cancelled caller receives a completed error instead of a cancellation. The late path's cause, a single Windows `move_directory_checked` taking 2 s or more (review N1), is a catalogue follow-on.
- [Cancellation teardown on Windows now fails against a wider class of holders (review S3)] → Before, cancellation removed the stage through std's POSIX-semantics `remove_dir_all`. A share-delete holder did not affect that removal, and only a holder without share-delete (or an image section) that was present at the moment of the single attempt defeated it. Now removal is the checked legacy-disposition removal, and any holder that outlasts `CLEANUP_RETRY_LIMIT` defeats it, including share-delete holders such as a scanner. So this change alters the shape of item 6's exposure but does not prove that exposure is smaller. It is the only removal the contract permits, and the leftover is now reported and receipted instead of hidden, so no code change follows.
- [A stage container that `PrivateTemp::new` creates but cannot finish is dropped unchecked (review S2)] → When `private_dir` fails after `tempdir_in` succeeds (provision.rs, the `StageLease::new(PrivateTemp::new(..)?, ..)` line), the container is dropped through `tempfile::TempDir::drop` while the lock is still held, and a failed removal is swallowed. This gap predates this change. The lock order is still correct, and the leftover is only an empty or near-empty `.install-*`. The ordering requirement is scoped to stages the lease owns rather than extending the checked close into `PrivateTemp::new`, which has other callers.
- [The retained-stage observation relies on a process-global test subscriber (decision 8)] → It is the only subscriber in the kuru-memory lib test binary, it observes only `kuru.memory` events and prints nothing, and its one installation gap fails loudly as a missing observation. A future test in this binary that needs its own global subscriber must share this recorder rather than install another. The observer's `try_lock` probe takes no spawn gate (review N3), and an observer panic inside `Drop` during an unwind aborts the test process (review N5); both are unchanged from the original capture.
- [`cfg(windows)` code cannot be compiled on the macOS authoring host] → windows-latest and windows-11-arm partitions compile and run it. They are named in verification.md as unrun locally.
